1. 核心结论

10,000 份文档对于中小型公司的知识库是合理规模，属于“中等偏真实”的测试集。但在当前 4C8G 数据层和 2C4G 应用层配置下，测试目标需要从“泛化极限压测”调整为“受资源约束的容量验收 + 渐进式极限探索”。

建议基准： 以 10,000 文档、50,000 到 80,000 chunk 作为当前部署的目标容量；100,000 chunk 以上先作为探索档，不建议一开始直接冲 500,000 chunk。
小规模验证 100 到 500 文档。用于验证文件格式、上传脚本、异步处理、索引和检索闭环。
目标规模 10,000 文档，约 50,000 到 80,000 chunk。用于确认当前服务器规格下的稳定性和可承载 QPS。
极限规模 先从 100,000 chunk 开始探索，再决定是否扩到更高容量。核心瓶颈预计是 ES/PG 同机 IO、embedding 调用和应用层 JVM。

2. 系统链路理解

当前项目的文档导入链路是异步架构：

  1. 上传接口接收文件：POST /api/v1/kb/{kbId}/documents。
  2. 后端校验文件类型和大小，计算 MD5，写入本地文件系统。
  3. 写入 documents 表，发送 RocketMQ 文档处理消息。
  4. Consumer 拉取消息，执行 DocumentPipelineService。
  5. Tika 解析文件文本，按知识库配置执行 512 字符切分、64 overlap。
  6. 调用 DashScope text-embedding-v4 批量生成 1024 维向量。
  7. 写入 document_chunks 表，并写入 ES 索引 ragforge_chunks。
  8. 文档状态更新为 completed 或 failed。

检索链路由 POST /api/v1/search 承载，支持以下策略：

策略 链路 性能特征 测试重点
keyword ES BM25 通常 QPS 最高 ES 查询延迟、分词效果、索引体积
vector query embedding + pgvector 受 embedding API 和 PG 向量索引影响 embedding 延迟、PG 慢查询、向量索引命中
hybrid vector + keyword 并行 + RRF 融合 耗时取决于更慢的一侧 并发任务池、PG/ES 同时受压
rewrite LLM 改写 + 多次 vector 比 vector 明显更重 改写模型延迟、放大后的向量查询次数
full rewrite + hybrid + rerank 最重链路，适合质量优先场景 端到端 P95、rerank 外部调用、降级行为

3. 当前部署约束

现有部署采用两台云服务器：数据与检索层集中在 4C8G ECS，应用入口层集中在 2C4G 轻量服务器。这个部署对于演示、轻量生产和中等规模知识库是可用的，但在万级文档导入和混合检索压测时，需要重点控制 ES、PG、RocketMQ 和 Java 后端的资源竞争。

服务器 规格 公网 IP 内网 IP 承载组件
ECS 云服务器 4 vCPU / 8 GiB / 40 GiB 系统盘 8.163.30.216 172.25.90.183 PostgreSQL、pgvector、Elasticsearch、Redis、RocketMQ
轻量级服务器 2 vCPU / 4 GiB / 50 GiB 系统盘 8.163.63.222 172.19.40.32 Nginx、前端服务、RAG Java 后端；后续可能部署 AI 求职 Agent 前后端

当前内存占用参考

组件 当前占用 / 限制 判断 测试影响
Elasticsearch 约 1.96 GiB / 3 GiB 已是数据层最大内存消费者 导入大量 chunk 后要重点观察 heap、GC、segment merge 和磁盘 IO。
RocketMQ Broker 386 MiB / 512 MiB 配置较紧 上传速度高于消费速度时，需要观察队列积压和重试。
RocketMQ NameServer 185 MiB / 256 MiB 轻量可接受 通常不是瓶颈，但仍需保留基础内存余量。
PostgreSQL 约 66 MiB 当前为空载或轻载状态 导入向量后占用会来自表、索引、连接、查询缓存和 checkpoint IO，不能按当前值乐观估算。
部署校准结论： 当前压测应优先验证 50,000 到 80,000 chunk 的稳定容量。ES heap 当前 3GiB 上限可以先保留，但 ECS 总内存超过 75% 或 ES GC 频繁时，应考虑降到 2GiB，并减少同机组件压力。

5. 万级文档数据规划

中小型公司真实知识库通常包含制度、流程、研发文档、产品资料、客户材料、会议纪要、FAQ、培训手册和故障复盘。10,000 份文档是合理的测试目标，但要控制文档长度分布，避免全部是短 FAQ 或全部是长 PDF。

类型 比例 数量 内容示例 用途
Markdown 30% 3,000 研发规范、接口说明、故障复盘、FAQ 模拟内部 wiki 和工程知识库
PDF 30% 3,000 培训材料、产品手册、制度文件、合同模板 覆盖 Tika/PDF 解析和版式文本抽取
HTML 25% 2,500 内部门户页面、帮助中心、SOP 页面 模拟网页知识沉淀
DOC/DOCX 15% 1,500 HR、法务、财务、销售材料 覆盖办公文档解析
注意： 当前后端文件白名单支持 pdf/doc/docx/md/markdown/html/htm，不支持 .txt。如果需要 text 文件，应先扩展文件类型校验；否则建议将纯文本保存为 .md。

文档长度分布

分档 数量 单篇长度 预估 chunk
短文档 7,000 800 到 2,000 中文字符 约 2 到 5 个
中文档 2,500 2,000 到 8,000 中文字符 约 5 到 18 个
长文档 500 8,000 到 30,000 中文字符 约 18 到 70 个

建议额外加入 5% 重复或近重复文档，用于测试 MD5 去重和覆盖上传；加入 2% 异常文档，用于测试空文件、损坏 PDF、错误 MIME、超大文件等健壮性场景。

6. 文档生成方案

不建议完全依赖 Ollama 逐篇自由生成 10,000 篇正文。这样耗时长、主题分布不可控、重复率难控制。更合理的方式是“少量 LLM 种子文档 + 结构化模板 + 程序化变体”。

推荐生成流程

用 Ollama 生成 200 到 500 篇高质量种子文档，覆盖 HR、财务、研发、产品、销售、客服、运维、法务等部门。
Python 根据模板扩展部门、岗位、项目名、产品名、日期、条款编号、客户行业、故障类型等变量。
生成 Markdown 和 HTML 原始文本，保证标题、段落、表格、列表、FAQ、流程编号等结构丰富。
将部分 Markdown/HTML 转换为 PDF 和 DOCX，模拟真实企业知识库的文件形态。
生成一份 manifest，例如 documents-manifest.jsonl，记录文件路径、业务域、预期关键词、关联问题和异常标记。

耗时估算

方案 估算耗时 优点 缺点
Ollama 全量逐篇生成 8 小时到 5 天，取决于 GPU/CPU 和模型 内容自然度较高 慢，分布不可控，重跑成本高
LLM 种子 + 模板扩展 30 分钟到 3 小时 速度快，可控，可复现 需要设计模板和变量池
纯模板生成 10 到 30 分钟 最快，最稳定 语义自然度不足，不适合质量评测

推荐采用第二种方案：先用 Ollama 生成种子，再由 Python 扩展到 10,000 份。这样既能控制领域覆盖，也能把生成耗时压到可接受范围。

7. 导入方案与耗时估算

不建议通过前端手工上传。应编写导入压测脚本，批量调用上传接口，并独立统计上传成功率、文档状态变化、MQ 堆积和最终 chunk 数。

导入流程

  1. 调用知识库接口创建测试知识库，记录 kbId。
  2. 扫描生成目录和 manifest，按文件类型、业务域、长度分层打乱。
  3. 多线程调用 POST /api/v1/kb/{kbId}/documents 上传。
  4. 上传并发从 2、5 逐步升高；当前服务器配置下不建议一开始使用 10+ 并发。
  5. 周期性查询 /api/v1/documents/{id}/status 或直接查询 DB 统计状态。
  6. 等待 pending/parsing/chunking/embedding/indexing 全部收敛，再启动检索压测。

按当前服务器配置调整后的导入批次

阶段 文档数 预估 chunk 目标
Smoke 100 500 到 1,000 验证所有文件格式可解析，确认上传脚本和状态统计可用。
Batch 1 500 2,500 到 5,000 验证上传并发 2 到 5 时是否稳定。
Batch 2 2,000 10,000 到 20,000 观察 ES/PG 磁盘增长、ES heap 和 RocketMQ lag。
Batch 3 5,000 25,000 到 50,000 第一次正式容量压测，确认导入耗时和检索 P95。
Batch 4 10,000 50,000 到 80,000 当前部署的目标容量验收。

导入耗时估算

当前 embedding batch size 最大为 10。如果 10,000 文档平均 5 到 8 个 chunk，总计约 50,000 到 80,000 chunk，需要约 5,000 到 8,000 次 embedding batch 调用。

单 batch embedding 耗时 纯 embedding 时间 加解析/DB/ES 后现实估算
0.5s 约 42 分钟 约 2 到 4 小时
1s 约 83 分钟 约 3 到 8 小时
2s 约 2.8 小时 约 6 到 14 小时
关键判断： 当前导入瓶颈大概率不是上传接口，而是 embedding API 限流、单 Consumer 串行处理、PG 单条 insert、ES bulk 写入，以及 ES/PG/RocketMQ 同机运行带来的磁盘 IO 竞争。

8. 性能与并发测试设计

检索压测阶梯

阶段 负载 持续时间 观察项
预热 2 到 5 QPS 5 分钟 连接池、JIT、ES/PG 缓存预热
低压 5 到 10 QPS 每档 10 分钟 P95、错误率、外部 API 响应
中压 20 到 50 QPS 每档 10 分钟 PG CPU、ES heap、应用线程
高压 50 QPS 以上按策略逐步探索 每档 10 分钟 错误率、超时、连接池耗尽、降级行为
稳定性 目标 QPS 的 70% 8 到 24 小时 内存泄漏、日志体积、慢查询增长、MQ lag

不同策略的目标建议

策略 建议目标 起测 QPS 说明
keyword 30 到 50 QPS，P95 < 500ms，错误率 < 0.5% 10 QPS 作为最高吞吐基线，主要压 ES。
vector 10 到 20 QPS，P95 < 2s，错误率 < 0.5% 2 QPS 重点看 query embedding 和 pgvector 查询。
hybrid 8 到 15 QPS，P95 < 3s 2 QPS 同时压 PG 和 ES，观察并行检索的线程资源。
rewrite 3 到 8 QPS，P95 < 4s 1 QPS 适合质量增强，不建议作为高 QPS 默认链路。
full 3 到 5 QPS，P95 < 6s 1 QPS 最重链路，主要用于质量优先和评测场景。

压测 query 集

准备 1,000 到 5,000 个 query，不能只用固定 query，避免缓存和热点导致数据失真。query 应覆盖：

  • 精确词查询，例如制度名称、接口名称、项目代号。
  • 模糊语义查询，例如“员工离职后账号怎么处理”。
  • 部门流程查询，例如“销售合同审批需要哪些材料”。
  • 跨文档归纳查询，例如“线上事故复盘通常需要包含哪些部分”。
  • 负样本查询，即知识库中没有答案的问题。

9. 观测与验收标准

当前项目已有检索日志表和基础 dashboard，但缺少完整的性能观测指标。压测前建议补齐以下指标。

观测维度 指标 用途
HTTP 请求量、P50/P95/P99、状态码、超时数 判断用户可见性能和错误率
Pipeline parse/chunk/embed/pg_insert/es_index 分段耗时 定位导入瓶颈
Embedding batch size、耗时、失败率、重试数、限流响应 判断外部模型调用容量
检索 rewrite/vector/es/rerank/log 分段耗时 定位不同策略的瓶颈
RocketMQ 队列积压、消费速率、重试次数、死信 判断异步导入是否跟得上上传速度
数据库 PG CPU、连接池、慢查询、索引扫描、表大小 判断 pgvector 查询和 chunk 写入瓶颈
Elasticsearch heap、GC、bulk 延迟、search latency、slowlog 判断关键词检索和索引写入瓶颈

通过标准

资源指标 警戒线 停止压测线
ECS 总内存 > 75% > 85% 持续 5 分钟
ES heap > 70% > 85% 或频繁 GC
系统盘/数据盘 可用空间 < 25% 可用空间 < 15%
PG / ES CPU > 70% > 90% 持续 5 分钟
RocketMQ lag 持续增长 30 分钟内没有下降趋势
文档 failed 比例 > 1% > 3%
  • 10,000 文档导入后，最终 completed 比例 >= 99%。
  • 知识库 doc_count、chunk_count 与实际表统计一致。
  • 导入期间 RocketMQ 无不可恢复堆积，失败文档可定位、可重试。
  • 目标 QPS 下错误率 < 1%，P95 达到各策略目标。
  • 稳定性测试期间 CPU、内存、连接池、ES heap 无持续恶化趋势。

10. 风险与优化建议

风险 影响 建议
40 GiB 系统盘空间不足 ES 索引、PG 向量表、上传文件和 Docker 日志共同增长，可能导致服务异常 建议挂独立数据盘，至少 100GB 起步；压测前清理日志并持续监控磁盘水位。
ES 与 PG 同机抢 IO 导入时 PG 写 chunk、ES bulk index 和 segment merge 同时打磁盘 分批导入，控制上传并发；必要时错峰执行大批量导入和检索压测。
外部 embedding API 限流 导入吞吐下降，大量文档卡在 embedding 增加限流器、重试退避、失败队列；压测时记录每批 embedding 耗时。
单 Consumer 串行处理 10,000 文档导入时间偏长 增加 Consumer 并发或分区消费，但要同步控制 embedding 并发上限。
PG 单条 insert chunk chunk 多时写入慢 改为 batch insert，降低事务和网络往返开销。
pgvector 索引参数固定 数据量升高后召回延迟或质量变化 对 50k、100k、500k chunk 分别测试 ivfflat lists/probes。
full 策略外部调用过多 QPS 低且尾延迟高 将 full 定位为质量优先链路，生产默认使用 hybrid 或 vector。
2C4G 应用层后续继续部署 Agent RAG Java 后端与 AI 求职 Agent 后端竞争 CPU、内存和连接 RAG 压测和 Agent 压测应分开执行；RAG Java 后端建议设置 -Xms512m -Xmx1536m。
缺少 Actuator/Micrometer 瓶颈定位依赖日志，效率低 补充 HTTP/JVM/DB/自定义 pipeline 指标。

11. 执行路线

阶段一 生成 100 到 500 文档，跑通生成、上传、异步导入、状态统计、检索压测脚本，确保闭环可重复。
阶段二 扩展到 2,000 文档，记录每 1,000 文档带来的磁盘增长、chunk 增长、导入耗时和 MQ 消费速率。
阶段三 扩展到 5,000 文档，第一次正式容量压测；分别测试 keyword、vector、hybrid、rewrite、full。
阶段四 扩到 10,000 文档，完成当前部署目标容量验收；如资源水位稳定，再探索 100,000 chunk 以上边界。

推荐先不要直接冲 10,000 文档。第一阶段用 100 到 500 文档把脚本、指标、数据质量、导入状态统计全部跑通，再按 2,000、5,000、10,000 分档扩大规模。否则一旦出现 embedding 限流、PDF 解析异常、ES heap 压力或磁盘空间问题，很难快速定位问题。
