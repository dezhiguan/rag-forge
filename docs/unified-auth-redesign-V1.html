1背景与目标

CareerMate 与 RAGForge 共用一个统一认证网关（Auth Gateway，事实上的 IdP）。当前两侧认证已基本统一，但账号注册体系、凭证/资料归属、权限粒度三方面口径不一致，需要一次收敛。

本次目标
  • 用手机号作为全局关联键，让同一自然人在 CareerMate 和 RAGForge 被识别为同一账号。
  • RAGForge 新增自助注册能力，并补齐用户名/邮箱/密码等凭证设置入口。
  • 明确凭证（全局，落网关）与资料（应用本地）的边界，杜绝"本地存密码导致登录不认"的隐患。
  • RAGForge 采用 GitHub 式账号模型（个人 / 组织），本期落地个人用户，组织作为后续演进。
  • 权限做到前端隐藏（体验）+ 后端拦截（安全）双层，列表接口做行级过滤。

3核心设计原则

3.1 三层分离：身份 / 准入 / 资料

概念归谁管含义
身份 IdentityAuth Gateway（一张 auth_users）"你是谁" —— 手机号/邮箱/用户名唯一
准入 Membership网关 user_app_membership"你能进哪个 App、以什么角色"，一行一个 App
资料 Profile各 App 本地库显示名 / 头像 / 简介，App 间互相独立

3.2 凭证 vs 资料（本方案最关键的一条线）

⚠ 凭证不能"本地保存"。 "在 RAG 设置密码/邮箱/用户名" 指的是入口/UI 在 RAG，但后端必须调网关写 auth_users，本地一个字都不存。否则：本地存的密码 → 登录走网关校验 password_hash → 网关不认 → 登不进。
类型例子存哪原因
凭证 Credential密码、邮箱、登录用户名、手机号网关 auth_users登录由网关校验；需全局唯一；两 App 共用
资料 Profile显示名、头像、简介App 本地各 App 可不同，网关不关心

注意区分两个"用户名"：登录用户名 username（全局唯一，网关）与显示名 displayName（本地，随便改）。

3.3 安全边界原则

  • 前端隐藏 = 体验，后端拦截 = 安全。 每个接口独立鉴权，绕过前端也必须 403。
  • 列表接口做行级过滤，不是"查全表再前端隐藏"。
  • 详情/检索/文档接口必须校验资源权限，防止猜 id 越权（IDOR）。
  • deny by default：默认拒绝，显式授权才放行。

4账号体系模型（GitHub 式）

RAGForge 定位类似 GitHub：账号有个人与组织两类，二者都是"命名空间（tenant）"，知识库挂在命名空间下。

GitHub本方案说明本期范围
个人账号user + 个人命名空间注册即拥有自己的命名空间，owner=本人V1
组织org 命名空间 + tenant_members创建者=OWNER，可邀请成员、建组织库V2 后续
repoknowledge_basevisibility = private / internal / publicV1（private/public）
本期（V1）只落地"个人用户 + public 公共库只读 + 自有库全权"。 组织、internal 可见性、团队权限作为 V2 演进，但表结构预留兼容。

5注册与账号关联

5.1 各端注册方式

端注册方式必要校验
CareerMate 移动端手机号验证码，注册登录一体（现状不动）短信验证
RAGForge（新增）邮箱 / 用户名注册必须短信验证手机号

5.2 手机号为关联键的合并逻辑（核心）

RAG 注册：填用户名/邮箱/密码 + 短信验证手机号
                       │
              网关按 phone_hash 查 auth_users
                       │
         ┌─────────────┴──────────────┐
   手机号不存在                  手机号已存在（CareerMate 注册过）
         │                            │
   新建 auth_users          ★ 走"补全 enrich"而非新建：
   + RAG membership            在同一行 auth_users 上补 username/email/password
         │                    + 增加 RAG membership
         │                    返回前端："该手机号已注册，已为你关联并补全"
         └─────────────┬──────────────┘
                 同一个 auth_users.id = 同一用户
这样就实现了你要的效果：只在 CareerMate 注册过的手机号用户，到 RAG 注册时被识别为同一人，在 RAG 补齐用户名/密码/邮箱，而不是产生重复账号。

5.3 多标识登录

登录支持 用户名 / 手机号 / 邮箱 任一作为 identifier，网关先归一化解析到同一 auth_users.id 再校验密码或验证码。移动端额外支持手机号验证码登录。

6凭证 / 资料 存储归属

字段落库位置RAG 后端职责CareerMate
手机号 phone_hash网关代理换绑（短信验证）注册即写
邮箱 email_hash网关代理绑定（验证）本期不做绑定
密码 password_hash网关代理设置/修改本期不做
登录用户名 username网关代理设置（唯一校验）本期不做
显示名 displayNameRAG 本地本地读写各自本地
头像 / 简介RAG 本地本地读写各自本地

CareerMate 维持现状（手机号注册，暂不做凭证绑定）；所有"补全凭证"动作集中在 RAGForge 的安全中心，统一代理到网关，改完两 App 全局生效。

7权限模型与默认权限

7.1 三层叠加（deny by default）

  1. 平台层：仅平台 staff（你）为超级 ADMIN，管运维 / 系统 KB / 成本中心。注册用户在平台层零特权。
  2. 命名空间层（V2）：tenant_members.org_role = OWNER / MEMBER。
  3. KB 资源层：visibility + kb_acl 协作者授权（read / write / admin）。

7.2 一次 KB 访问的判定顺序

是平台 ADMIN？           → 运维通道（默认不读业务私库，读则留审计）
是 KB owner？            → admin（全权）
kb_acl 有显式授权？      → 按 read / write / admin
（V2）org MEMBER 且 internal？ → read
visibility = public？    → read（只读）
否则                     → deny + 记 kb_access_denied

7.3 本期普通个人用户的默认权限

能力普通个人用户平台 ADMIN
读平台 public 知识库可（只读）可
新建自己的知识库可可
自有库读写/删除（admin）可可
检索 / 应答（自有 + public）可可
他人私有库不可见默认不可见；需破玻璃（X-Admin-Override + 原因）方可读，且留审计
API Key 管理 / 成本中心 / 维护禁止可
kb_type=SYSTEM 系统库禁止禁止（已挡）
性能诊断 / 质量看板 / 全局指标禁止可

8查询接口行级权限

同一个接口、不同人返回不同的行，过滤在 SQL/服务层完成，不在前端。

8.1 GET /api/v1/knowledge-bases 两种 WHERE

普通个人用户 
WHERE kb_type != 'SYSTEM'
  AND (
       owner_user_id = :me
    OR visibility = 'public'
    OR id IN (SELECT kb_id FROM kb_acl
              WHERE principal_type='user'
                AND principal_id=:me)
  )
平台 ADMIN 
WHERE kb_type != 'SYSTEM'
  -- 其余全看

复用 KbAccessGuard.allReadableKbIds() / filterReadable()：先算 readableKbIds，再 WHERE id IN (:ids)。

8.2 每行附带"我的权限"

[
  {"id":12,"name":"我的简历库","visibility":"private","myPermission":"admin"},
  {"id":3, "name":"平台公共法律库","visibility":"public","myPermission":"read"}
]

前端据 myPermission 决定"编辑/删除"按钮是否 disabled。

8.3 三个不能省的点

  • 详情接口必校验：GET /kb/{id} 必须 canRead，防猜 id 越权。
  • count / 分页基于过滤后集合，避免泄露"有多少看不到的库"。
  • 列表 / 详情 / 检索 / 文档四类入口共用同一个 KbAccessGuard，保持一致。

有权但当前状态不可操作（对只读库的编辑按钮）展示但 disabled + tooltip让用户知道功能存在及如何获得权限

9.3 实现方式

  • /me 返回 role + 能力清单（如 ["kb:read","kb:own:write","search:run","answer:run"]）。
  • 前端菜单每项挂 requires，/me 没有就不渲染（非 disabled）。
  • 后端每个 controller 方法 @PreAuthorize(...) + 资源走 KbAccessGuard —— 真边界。

11改造清单与数据库变更

11.1 Auth Gateway（改动最大）

  • 新增注册 / 账号补全接口：按 phone_hash 判断"新建 vs 补全(enrich)"。
  • 新增凭证补全接口：设密码 / 绑邮箱 / 设用户名，全部带唯一校验 + 验证。
  • 迁移：phone_hash / email_hash / username 加 UNIQUE 约束。
  • 新增 user_app_membership(user_id, app, role, status, created_at)，一行一个 App。
  • 确认 /auth/login/password 的 account 能解析 用户名/邮箱/手机号。
  • 敏感变更（改密码/换手机）触发 password.changed 事件，旧 token 失效（已有 webhook）。

11.2 RAGForge

  • AuthProxyController 新增：/register、注册场景 /sms/send、/credential/set-password、/credential/bind-email、/credential/set-username —— 全部代理网关。
  • 新增 RAG 本地 profile 表：user_profile(auth_user_id, display_name, avatar, bio, created_at)。
  • 新增 GET/PUT /api/v1/profile 与聚合 GET /api/v1/me。
  • 默认权限落地：新注册 → membership(rag, USER)；KbAccessGuard 补 public 只读 放行；种一批 public KB。
  • 列表/详情/检索接口统一行级过滤；列表行附 myPermission。
  • 前端：注册页、菜单按 capabilities 显隐、个人设置页、安全中心页、显示名兜底。

11.3 CareerMate（按现状不动）

  • 仅确认：注册写入的 auth_users 与 RAG 同网关、同表、同 issuer。
  • 依赖网关"手机号已存在则补全"逻辑与 RAG 打通，无需改动 CareerMate 代码。

11.4 数据库变更汇总

库变更类型
网关auth_users 加 UNIQUE(phone_hash / email_hash / username)迁移
网关新增 user_app_membership建表

12任务拆分（执行顺序）

  1. GW-1 网关：auth_users 唯一约束迁移 + user_app_membership 建表。
  2. GW-2 网关：注册 / 补全(enrich) 接口（手机号为键的新建 vs 补全）。
  3. GW-3 网关：凭证补全接口（密码/邮箱/用户名，唯一校验 + 验证）+ 多标识登录确认。
  4. RAG-1 RAG：user_profile 建表 + /api/v1/profile + /api/v1/me 聚合。
  5. RAG-2 RAG：AuthProxyController 注册与凭证代理接口。
  6. RAG-3 RAG：默认权限（membership=USER）+ KbAccessGuard public 只读 + 种子 public KB。
  7. RAG-4 RAG：列表/详情/检索行级过滤 + myPermission 字段。
  8. RAG-5 前端：注册页 + 菜单显隐（capabilities）+ 个人设置 + 安全中心 + 显示名兜底。
  9. QA 验收：Playwright 覆盖"CareerMate 手机号用户到 RAG 补全"、"普通用户列表只见自有+public"、"越权 403"、"管理项不渲染"。

每个任务交付前需含：禁止项、字段设计、验收标准（Playwright），与既定协作规范一致。

13范围与非目标

V1 范围
  • RAG 自助注册 + 手机号关联补全
  • 凭证/资料分层落地
  • 个人用户默认权限（public 只读 + 自有库全权）
  • 行级权限 + 前端菜单/按钮控权
  • 个人设置 / 安全中心 / /me
非目标（后续 V2）
  • 组织（org）账号与 tenant_members
  • internal 可见性与团队权限
  • CareerMate 侧凭证绑定入口
  • Web 托管登录页（OIDC Authorization Code）
  • Agent 委托链（consent/delegation）审计闭环

13.1 既有能力（本期不改，仅纳入回归）

下列已在现有代码中实现，本方案不改其机制，但其安全边界须随本次改造一并回归（详见测试方案 Part C/D/E）：

  • MCP / SSE 鉴权：/mcp/**、/sse 经 Bearer JWT 或 X-API-Key，ApiKeyInterceptor 以 allowed_kb_ids 限定服务账号可达 KB。
  • CareerMate → RAGForge 跨服务调用：经网关 oauth/token-exchange 换 ragforge-api/rag:search 短 TTL token，不复用自身受众 token。
  • Agent 工具权限/风险：AgentToolPermission / AgentToolRiskLevel，高风险写入经 pending-action / 工具卡片承接。

13.2 待决策项

会话策略：多会话并存 vs 单点互斥。 当前为多会话并存（A 登录后 B 再登录不挤掉 A，各自独立 session/refresh），仅 logout / logout-all 主动撤销。若需"新登录踢旧登录"，需在登录时按 user_id 撤销其它 active session，或用 session_version 自增使旧 token 失效。 对应测试用例 TC-LOG-10：当前断言"多会话并存"，若改单点互斥需反转断言。
其它待决策：① 邮箱绑定走邮件验证还是短信验证；② 应答/检索的普通用户配额阈值；③ 个人 API Key 轻量入口是否纳入 V1。
