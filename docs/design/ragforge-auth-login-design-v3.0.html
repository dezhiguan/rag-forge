1. 角色模型 F1

问题：v2.0 写「ADMIN 或 kb_acl 任意条目即可进后台」是危险的。一个只对单个 KB 有 read 权限的用户不应该看见 API Key 管理、评测、系统配置、审计日志、其它人的 KB 列表。这等于把单 KB 读权限放大成"准管理员"。

1.1 三级角色定义

角色判定条件（任一即得）语义典型场景
ADMIN platform_role == 'ADMIN' RAGForge 平台管理员 @guandezhi · 运营负责人
KB_EDITOR kb_acl 中至少一条 permission ∈ {write, admin} 对至少一个 KB 有写权限的运营/数据同学 导入语料、跑评测
KB_VIEWER kb_acl 中只有 permission == read 只读访客 业务方临时查询
（无） 以上都不满足 无权访问 403 PLATFORM_ROLE_DENIED
角色不是数据库列：角色是一个派生概念，由 platform_role 和 kb_acl 实时计算。JWT 签发时把派生结果作为 rag_role claim 写进去（避免每次请求重算），但权威仍然是 kb_acl 表。

1.2 JWT 中的 rag_role claim（新增）

{
  "aud": "ragforge-admin-api",
  "sub": "user:26",
  "principal_type": "user",
  "user_id": 26,
  "tenant_id": "tn_01J_PERSONAL",
  "platform_role": "USER",              // 平台层级
  "rag_role": "KB_EDITOR",              // ← 新增：RAGForge 派生角色
  "rag_writable_kb_ids": [16, 17],      // ← 新增：可写 KB 显式列表（KB_EDITOR/ADMIN 才有）
  "rag_readable_kb_ids": [15, 16, 17, 18, 19],  // ← 新增：可读 KB 列表
  "scopes": ["rag:admin:read"],         // ADMIN 可有 rag:admin:write 等
  "session_id": "sid_xxx", "jti": "jti_xxx", "exp": 1781800900
}
长度风险：若 KB 数极多（> 50），rag_readable_kb_ids 改为只放 ID 前缀或"all"标记，详细列表由 RAGForge 每次请求查 kb_acl 缓存（30s TTL）兜底。第一版 KB < 20，直接放完整列表即可。

public boolean canRead(Long kbId) {
  return ctx.readableKbIds.contains(kbId)
      && kbAclMapper.existsByUserAndKb(ctx.userId, kbId, "read|write|admin");
}

3. Cookie 边界与 BFF refresh F2

v2.0 矛盾："refresh cookie 写到 admin.ragforge.cn" 与"前端调 auth.careermate.cn/auth/token/refresh" 不可能同时成立—— cookie 不会跨域自动携带。必须二选一。

3.1 选型：RAGForge BFF 模式（推荐 · 第一版采用）

方案优势劣势是否采用
A · BFF 模式
refresh cookie 落 admin.ragforge.cn
前端 → RAGForge BFF → Auth Gateway		 无跨域；CSRF 处理简单；client_secret 不暴露给浏览器；可独立做风控 RAGForge BFF 多一跳；BFF 需要持有 client 私钥 ✅ v3.0 采用
B · 跨子域 Cookie
cookie 写 .careermate.cn（或共享根域）		 少一跳 必须双根域共享 → 不可能（admin.ragforge.cn ≠ *.careermate.cn）；CSRF 复杂；SameSite=None 必须 Secure；前端直连暴露设计 ❌ 不采用

3.2 BFF 全量端点表

前端调RAGForge BFF 路径BFF 做什么转调 Auth Gateway
登录（密码） POST /api/auth/login 读 body → 注入 client_assertion + target_aud=ragforge-admin-api → 收到 token → refresh 落自身 Cookie，access 回包给浏览器 POST /auth/login/password
登录（手机） POST /api/auth/login-mobile 同上 POST /auth/login/mobile
发短信 POST /api/auth/sms/send 透传（不带 client_assertion，按 Auth GW 公开端点） POST /auth/sms/send
刷新 POST /api/auth/refresh F2 从 admin.ragforge.cn Cookie 读 refresh → 注入 client_assertion → 调 Auth GW；新 refresh 写回 Cookie，新 access 返回前端 POST /auth/token/refresh
登出（本端） POST /api/auth/logout 读 refresh → 调 Auth GW 吊销 → 清自身 Cookie POST /auth/logout
登出（全端） POST /api/auth/logout-all 读 refresh + body password → 调 Auth GW logout-all POST /auth/logout-all
忘记密码 POST /api/auth/password/reset/{init|verify|confirm} 透传 + 在 confirm 成功后顺手登 RAGForge（再调一次 login） POST /auth/password/reset/*
userinfo GET /api/auth/userinfo 透传 Bearer GET /userinfo

3.3 Cookie 规范

Set-Cookie: rf_refresh=<opaque>;
            Domain=admin.ragforge.cn;
            Path=/api/auth;                 ← 仅 BFF 路径可见，缩小暴露面
            HttpOnly;
            Secure;
            SameSite=Lax;
            Max-Age=2592000                  ← 30 天，滑动过期由服务端维护

3.4 CSRF

  • BFF 所有写接口（login/refresh/logout/...）必须校验 Origin header（仅允许 https://admin.ragforge.cn）。
  • 额外加 double-submit CSRF token：登录成功时下发 rf_csrf cookie（非 HttpOnly），前端读出来回填到 X-CSRF-Token header，BFF 比对。
  • GET 请求不校验 CSRF；BFF 不暴露任何把 cookie 当鉴权的 GET 写操作。

4. 客户端认证标准格式 F5

v2.0 错误：把 client_assertion 当作 Bearer 放 Authorization 头，违反 RFC 7523 / RFC 8414。Authorization: Bearer 在 token 端点用于 subject_token（用户身份），不能用来传 client 自己的 assertion。

4.1 正确格式（RFC 7523 §2.2 + RFC 6749）

POST /auth/login/password HTTP/1.1
Host: auth.careermate.cn
Content-Type: application/x-www-form-urlencoded

# 用户业务参数
account=guandezhi@ragforge.cn
&password=...
&target_aud=ragforge-admin-api

# 客户端认证三件套（RFC 7523）
&client_id=ragforge-admin-backend
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=eyJhbGciOiJSUzI1NiIs...                ← 短期 JWT，10 分钟有效

4.2 client_assertion JWT 结构

{
  "iss": "ragforge-admin-backend",          // = client_id
  "sub": "ragforge-admin-backend",          // = client_id
  "aud": "https://auth.careermate.cn/oauth/token",   // 必须等于 token endpoint URL
  "jti": "ca_01J7Q...",                     // 一次性，Auth GW 防重放
  "iat": 1781800000,
  "exp": 1781800600                         // ≤ 10 分钟
}

4.3 token-exchange 同样格式

POST /oauth/token-exchange HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=eyJ...                       ← 用户 access_token
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&requested_audience=ragforge-api
&requested_scopes=rag:search
&client_id=careermate-backend
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=eyJ...

4.4 dev 期降级：client_secret_basic

POST /auth/login/password HTTP/1.1
Authorization: Basic base64(ragforge-admin-backend:<secret>)
Content-Type: application/x-www-form-urlencoded

account=...&password=...&target_aud=ragforge-admin-api
仅在 spring.profiles.active=dev 时启用 client_secret_basic；prod 必须 private_key_jwt。

CREATE TABLE kb_acl (
  id              BIGSERIAL PRIMARY KEY,

CREATE INDEX idx_kb_acl_kb        ON kb_acl(kb_id);

-- owner 自动入 ACL（admin 权限）

SELECT id, 'user', 'user:' || owner_user_id, 'admin'

// 2. visibility 二次过滤（SYSTEM 仅 service_account 可见）
if (ctx.principalType.equals("user")) {

// 3. 向量、BM25、RRF 全链路都加 kb_id IN (?)
chunkMapper.searchVector(readableKbIds, queryVector, topK);

7. RAGForge 登录数据流（合并修订）

Browser (admin.ragforge.cn)
  POST /api/auth/login                              ← BFF 入口
  body: { account, password }
  Origin: https://admin.ragforge.cn

RAGForge BFF (ragforge-admin-backend)
  · 校验 Origin
  · 构造 client_assertion JWT（RS256, 10min）       [FIX F5]
  · 调 POST https://auth.careermate.cn/auth/login/password
    Content-Type: application/x-www-form-urlencoded
    body: account, password, target_aud,
          client_id, client_assertion_type, client_assertion

Auth Gateway
  · 校验 client_assertion 签名（用 RAGForge 公钥）
  · 校验 client_id 允许 target_aud=ragforge-admin-api
  · 校验账号密码 + 风控
  · 查 platform_role + kb_acl 派生 rag_role
    ├─ 既非 ADMIN 也无任何 kb_acl 条目 → 403 PLATFORM_ROLE_DENIED
    └─ 否则签发：
       access_token  (aud=ragforge-admin-api, 15min, 含 rag_role + rag_*_kb_ids)
       refresh_token (7d, family_id)
  → 返回 RAGForge BFF

RAGForge BFF
  · refresh → Set-Cookie rf_refresh, Domain=admin.ragforge.cn, Path=/api/auth   [FIX F2]
  · 下发 rf_csrf cookie（非 HttpOnly）
  · access 在 response body 返回浏览器（前端存内存）
  → 200 OK

Browser
  · access 存 Pinia store（内存）
  · 后续请求：Authorization: Bearer <access>  +  X-CSRF-Token: <rf_csrf>

Access 过期：
Browser → POST /api/auth/refresh （带 rf_refresh cookie + X-CSRF-Token）
RAGForge BFF → 同样注入 client_assertion → Auth GW /auth/token/refresh
→ 新 refresh 重写 cookie；新 access 返回

8. 租户在 UI 上的处理

v3.0 决策：第一版 RAGForge UI 不暴露"租户切换器"，KB 列表按 visibility 分组展示（公共 / 个人 / 系统）， tenant_id 作为后端数据隔离实现细节。等真做企业版 (TENANT visibility) 再加 UI 切换器。
  • 首次登录时如发现 user 无个人租户，BFF 调 CareerMate 创建（沿用 v1.2 §6 补偿逻辑），失败则 RAGForge 登录 403 并提示"个人租户未就绪，请稍后重试"。
  • 顶栏头像下露出 tenant_slug（如 personal-26），仅作信息展示，不可点击切换。
  • KB 列表分组：公共知识库 (PUBLIC) / 我的知识库 (PRIVATE, owner=self) / 已授权 (PRIVATE, ACL 授权)；SYSTEM 仅 ADMIN 可见且独立分组。
