1背景与根因

质量看板 /evaluation/quality 以 LLM-as-Judge 评测知识库应答质量（忠实度 / 上下文精度 / 答案相关性 / 综合），数据来源分 PRODUCTION（线上流量抽样）/ GOLDEN_SET（黄金集回放）/ MANUAL。黑盒 QA（2026-07-04，ragforge.net）实测确认：看板渲染本身无缺陷 —— 管理员触发回放后其 org 看板 15 秒内出全量数据；各普通账号看板全 0 是因为其 org 确实没有判分样本，非取数缺陷。

根因：一套机制同时承载了两种本不相同的诉求。「黄金集 + 回放」被当作平台基准来实现（全局题集、admin-only、平台预算），但看板与样本却是组织级口径（org 隔离）。二者对不上，于是产生三处割裂。

三处割裂（实测）

  • 每个 org 的设置抽屉都显示「启用题数：20」—— 这是平台全局值，却摆在租户面前，像是自己的回归集。
  • 样本 org 级隔离，回放又只灌触发者自己的 org（实测：管理员 org 出数、其余 org 全 0）→ 租户永远拿不到。
  • 抽屉写「全量黄金集回放」，实际只作用于一个 org，名不副实。

综合结果：普通租户既被平台基准的控件误导，又落到「查也没用、点也没权限」的死胡同。

2决策：收敛为「平台基准单轨」

与其把一套拆成双轨，不如先明确黄金集的定位 —— 它就是一个固定的平台基准，不下放给租户。这与既有的 Core Set「100 题冻结、禁止再扩展」决策一致，且改动最小。

结论：黄金集 = 固定 100 题的平台基准，只服务平台侧质量监控，不进任何租户看板。租户看板由「生产流量抽样」驱动。「组织回归集」（租户自助回归）留作 backlog，待真有诉求再评估。

❌ 现状（概念混淆）

↓ 回放

↓

平台侧 固定 100 题 × 冻结基线库 → 平台健康视图
— 完全隔离 —
租户侧 生产流量抽样 → 本 org 看板
↓

3平台基准轨的完整构成

「固定 100 题」只是题集固定；题终究要跑在一个知识库上才能检索出答案，所以基准要题集与语料一起冻结，且由平台自持。

组成要求为什么
固定题集100 题冻结、禁止再扩展（沿用 Core Set 决策）基准的可比性来自题不变
冻结基线知识库
（golden corpus）		内容冻结、版本化，题集绑定其上基准要测的是「链路本身」是否退化；若语料随内容增删漂移，分数变化就分不清是链路退化还是内容变了 —— 信号被污染
系统组织自持基线库挂在专属系统/平台组织下，防删 + 版本化个人 org 易失：本次 QA 实测 KB 640 随 org 319 清理一起消失；基线库若寄居私人 org，组织一动基准即失效
回放归属回放样本落系统组织 → 平台健康视图；仅「全平台视图 / 破玻璃」可见可触发，改名「平台基准回放」名副其实；且不再污染任何租户看板
关键澄清：「固定不变」要同时管住题集与语料。题：固定 100 条；语料：绑一个内容冻结的基线知识库。两者都冻结，回放分数的 delta 才等于「链路健康度」。

为什么固定输入、结果仍会变（信号 vs 噪声）

固定题 + 固定库 ≠ 固定结果 —— 而「结果会变」正是基准存在的意义：把输入冻住，是为了让输出的任何变化都能归因到「链路本身」。影响回放结果的因素分两类：

类别具体因素如何对待
甲 · 信号
（你主动改的，正是要检测的）		 Embedding 模型/版本、分块策略/size/overlap、检索参数（hybrid 权重/topK/阈值）、Rerank 模型、Rewrite、应答模型/prompt、Judge 模型/prompt、索引与分词（ES/IK 版本） 要「检测」—— 这就是回归门禁的价值
乙 · 噪声/漂移
（你没改也会变）		 LLM 采样非确定性（temperature）、Judge 本身方差、DashScope 供应商侧模型静默升级（配置没动、云端权重变了）、失败/超时/限流致样本缺失 要「控制/扣除」—— 别把噪声当退化
配套三件事（让基准可用）：
  • 压确定性：应答 greedy / temperature=0，Judge 固定 prompt（必要时多次取平均降方差）；
  • 测噪声带：同配置连跑 N 次，量出「什么都没改时的自然波动范围」，低于带宽的变化视为噪声、不告警；
  • 记链路指纹：每次回放存下当次的模型 id/版本、检索参数、索引版本、prompt hash —— 分数一动即可归因到「哪次改动 / 哪个模型漂移」。没有指纹，分数动了也解释不清。

价值不在「某一次的绝对分」，而在跨时间、跨改动的对比：固定输入让对比干净，结果变不变取决于你的链路和供应商动没动。

4落地方案

阶段一 · 平台基准归位 + 租户止血目标 2026-07-08 前

平台侧（基准归位）

  • 建/指定专属系统组织，将黄金集绑定的基线知识库迁入并冻结（防删标记 + 版本化）；100 题固定。
  • 回放样本归属系统组织，进平台健康视图；回放入口收敛到「全平台视图」，字样由「全量黄金集回放」改为「平台基准回放」。
  • 每次回放记录链路指纹（模型 id/版本、检索参数、索引版本、prompt hash）；应答 greedy/temperature=0，先跑 N 次测出噪声带作为告警阈值基线。

租户侧（止血收敛，纯口径/可见性，零新表）

  • 普通租户看板隐藏黄金集回放控件与「启用题数」等平台全局值（如需展示则明确标注「平台基准 · 只读」）。
  • 租户看板空态改为诚实引导：「质量数据来自你的线上流量抽样判分，随着应答使用量增加将自动显示」（已在近期修复中改过一版文案，配合再收口）。

验收：普通租户看不到任何「看似自己、实则动不了」的黄金集控件；平台基准回放仅平台管理员可见可触发、样本落系统组织；基线库带防删标记；ragforge.net Playwright 断言覆盖两类角色可见性差异。

阶段二 · 组织回归集 Backlog待租户诉求验证后评估

若后续确有租户提出「想一键验证自己库改动后的质量」，再评估开放组织回归集：org 内选题 + 绑定自己 KB、组织管理员自助回放、样本落本 org、计本 org 预算。

前置硬约束（届时必须先做）：预算隔离。org 级回放必须走 org 预算账，绝不能记平台预算 —— 否则一开放自助就会打爆平台 judge 预算（这也是当初做成 admin-only 的真实原因）。

5取舍与成功指标

单轨的取舍：最省事、不碰 Core Set 冻结约束，代价是租户没有「确定性看自己质量」的手段，完全靠生产流量 —— 刚上手、流量少的团队看板会空一阵子。本方案判断该代价可接受；真有强诉求再走阶段二。

成功指标

租户误导消除
普通租户不再出现无法操作的黄金集控件
平台基准稳定性
基线库防删、版本化，回放 delta 可归因到链路
平台 judge 预算
回放成本计入平台账、可控不超支

6待架构拍板

  • 确认单轨方向：黄金集定为固定 100 题平台基准、不下放租户；「组织回归集」入 backlog。
  • 确认基线库归属：由专属系统组织自持、冻结、防删、版本化；与既有 Core Set「冻结不扩展」一致（Core Set 归平台基准轨，不受组织级概念影响）。
以上两点确认后即可开工阶段一（纯收敛 + 基准归位，风险低，本周可上线）。
