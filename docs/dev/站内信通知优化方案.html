1. 现状与问题

两轮代码走查后，邀请通知链路存在两处断点，一处硬缺口。核心症结：通知只在"发起邀请"那一刻落库一次，之后再无任何服务端 → 客户端的推送或回写。

事件后端是否落库通知接收方能否感知问题定级
A 邀请 B 有 给 B insert 一条 ORG_INVITE 需刷新 前端仅挂载时拉一次，无轮询/推送 体验缺陷
B 接受 / 拒绝 无 完全未给 A 回写 无从感知 连数据都不存在 硬缺口

关键代码事实

  • InvitationService.accept()（L145-161）只做三件事：插入 org_members、邀请状态置 ACCEPTED、把接受者自己那条通知标已读。无任何指向发起方的 insert。
  • 邀请表 OrgInvitation.inviterUserId 发起时已写入（L86），但在 accept/decline 流程从未被读取 —— 回写所需数据一直都在，只是没人用。
  • 前端 NotificationBell.vue：唯一取数在 watch(isAuthenticated,…,{immediate:true})（L78），无 setInterval、无 WebSocket、无 SSE；接受后 window.location.reload() 只刷新接受者自己。
  • 后端全库 grep WebSocket 零命中；unreadCount() 接口前端根本没被调用。

2. 优化目标

  1. 补数据（P0）：B 接受 / 拒绝邀请后，服务端给发起方 A 落库一条回执通知（"B 已接受/拒绝加入 XX 组织"）。
  2. 接链路（P0）：铃铛角标合并为统一未读数（邀请 + 通知）、接通 unread-count，点开分区展示，让"未读数"真实可用。
  3. 做触达（P1）：通过 SSE 让新通知无需手动刷新即秒级出现在接收方界面。
  4. 补对称（P1）：decline 与 accept 同等处理，消除"拒绝"这个感知黑洞。
优先级判断：P0 两项是"信息根本不存在 / 显示错数据"的正确性问题，纯后端 + 前端小改，必做且成本低；P1 触达采用 SSE（单向实时、依赖现成），可独立排期。不上 WebSocket —— 对单向通知场景是过度设计。

3. 数据模型设计

复用现有 notifications 表，不新增表。仅扩展通知类型枚举：

type（枚举）触发时机收件人refId状态
ORG_INVITEA 发起邀请被邀请方 BinvitationId现有
ORG_INVITE_ACCEPTEDB 接受发起方 A（inviterUserId）invitationId新增
ORG_INVITE_DECLINEDB 拒绝发起方 A（inviterUserId）invitationId新增

回执通知字段约定

  • userId = inv.inviterUserId（复用已有死字段，本方案让它"活"起来）
  • title / content = "{接受者昵称} 已接受加入 {组织名} 的邀请"（拒绝同理）
  • refId = invitationId；readAt = null（未读）
  • 幂等：同一 invitationId + 同一 type 只允许一条回执，避免重复点击/重试产生多条（见 §5 幂等要求）

4. 总体方案（三层）

第一层 · 数据回写（P0，纯后端）

B 点击接受→ accept() 原有三步→ 新增：给 inviterUserId insert 回执通知→ A 的 unread-count +1

改动点集中在 InvitationService.accept() 与 decline() 末尾，复用现有 notificationMapper。不改接口签名、不改前端接受逻辑。

第二层 · 前端角标与面板（统一未读数 + 分区展示）已定

角标：铃铛当前错误地显示"待处理邀请数(pending)"。改为统一未读数 = 待处理邀请 + 未读通知（回执等）之和，数据源接通 unread-count。

面板：点开铃铛后分区展示，用户一眼分清「需要我操作的」和「仅告知的」：

分区内容可操作项
① 待处理邀请别人邀请我加入组织（PENDING）接受 / 拒绝
② 通知回执类（ORG_INVITE_ACCEPTED/DECLINED）等只读消息标记已读 / 全部已读
口径统一：角标数字与面板两区未读之和一致；任一区被消费（接受邀请 / 标记已读）后，角标同步递减。

第三层 · 实时触达 —— 采用 SSE 已定

放弃轮询，直接走 SSE（Server-Sent Events）：后端按用户维持一条长连接，通知落库即 push，前端 EventSource 收到后刷新未读数/列表，无需手动刷新、无轮询空转。选它的理由：

  • 站内通知是纯服务端 → 客户端单向场景，SSE 恰好匹配，比 WebSocket 轻。
  • rag-forge 已引入 Spring AI MCP WebMVC-SSE 依赖，SSE 技术栈是现成的，接入成本低。
  • 浏览器原生 EventSource 自带断线重连，前端实现简单。
方案结论说明
SSE✔ 采用单向实时、依赖现成、原生重连
前端轮询降级备选仅当 SSE 因网关/代理不可用时作为 fallback
WebSocket/STOMP✘ 不采用双向能力对单向通知过度设计
SSE 关键设计点（供评审）：
  • 连接维度：按 userId 维持 emitter（一个用户可多标签页 → 多 emitter，用 ConcurrentHashMap<userId, List<Emitter>> 管理）。
  • 鉴权：SSE 端点复用 JWT 鉴权，连接建立时校验用户身份。
  • 推送时机：通知 insert 成功后（同事务提交后）向对应 userId 的 emitter 推 unread-count 变更事件。
  • 心跳与超时（已定）：服务端每 25s 发一次心跳（comment/ping）保活；SseEmitter 服务端 timeout 设 30min，到时正常结束、由前端 EventSource 自动重连兜底。
  • 入口层（已定）：Nginx 对 SSE 路由 proxy_buffering off + proxy_http_version 1.1 + proxy_read_timeout 300s（> 心跳间隔即可），避免入口掐断长连接。
  • 多副本（本期即做）：api 3 副本，SSE 连接落单副本；推送经 Redis Pub/Sub 广播，命中持有该 userId emitter 的副本再下发（复用现有 Redis）。

5. 后端改动点与约束

文件 / 位置改动
InvitationService.accept() L145-161 末尾读取 inv.getInviterUserId()，insert 一条 ORG_INVITE_ACCEPTED 回执（幂等）
InvitationService.decline()对称新增 ORG_INVITE_DECLINED 回执（幂等）
通知类型枚举 / 常量新增两个 type 常量
新增 SSE 端点（如 GET /api/v1/notifications/stream）SseEmitter：按 userId 维持连接、JWT 鉴权、心跳保活；提供统一的 NotificationPusher 供落库后调用
通知 insert 落点（accept/decline 等）事务提交后调用 NotificationPusher.push(userId, unreadCount)
多副本广播（Redis Pub/Sub）推送事件经 Redis 广播，命中持有该 userId emitter 的副本再下发（复用现有 Redis）
NotificationBell.vue L37-44 / L78角标改用统一 unread-count；面板分区；建立 EventSource 订阅 /stream，收到事件即刷新（去掉 accept 后的整页 reload）

硬性约束（执行禁止项）

  • 幂等：回写前先查 (refId=invitationId, type=…, userId=inviterUserId) 是否已存在，存在则跳过，禁止产生重复通知。
  • 回执 insert 必须在 accept/decline 的同一事务内，随主流程一起提交/回滚。
  • 发起方已注销 / inviterUserId 为空时安全跳过，不得抛异常中断接受主流程。
  • 禁止改动 accept/decline 的接口签名与返回结构。
  • 禁止引入 WebSocket/STOMP —— 触达统一走 SSE。
  • SSE 推送必须在事务提交之后，不得在事务内推送（否则回滚后会推出脏未读数）。
  • SSE 端点须做 emitter 生命周期管理：onCompletion / onTimeout / onError 时从 map 移除，防止内存泄漏。
  • 推送失败（连接已断）不得影响主业务；SSE 仅为触达增强，未读数最终以接口查询为准（前端连上后先拉一次做对齐）。

7. 验收标准（Playwright）

  • A 邀请 B → B 接受 → A 刷新页面，铃铛角标 +1，通知列表出现"B 已接受加入 XX 组织"。
  • A 邀请 B → B 拒绝 → A 侧出现对应的"已拒绝"回执。
  • B 重复点击接受 / 接口重试 → A 侧回执仅一条（幂等验证）。
  • 角标 = 待处理邀请 + 未读通知之和；点开面板分两区展示；任一区被消费后角标同步递减。
  • 点击回执标记已读后，unread-count 相应递减。
  • （P1·SSE）A 保持页面不动，B 接受后 A 端无需手动刷新，角标自动 +1（秒级）。
  • （P1·SSE）断网后重连，EventSource 自动恢复；重连后前端拉一次 unread-count 与服务端对齐。
  • （P1·SSE）多标签页登录同一用户，各标签页均能收到推送。
  • 发起方为空 / 已注销场景下，B 接受流程正常完成、不报错。
