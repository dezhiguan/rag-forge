1现状与问题

REST(/api/v1/search·answer·documents)与 MCP(/mcp·/sse)对外接入,共用 RagAuthContext + KbAccessGuard 判权。经核实,当前存在以下问题:

#问题(以代码为准)级别
1对 API Key 而言 org_id 不是隔离维度:服务账号 userId=null,org/ACL 分支全短路,可读集 = allowed_kb_ids ∪ 全站 PUBLIC,与 Key 的 org 无关P1
2跨组织 PUBLIC 全局可读:任一有效 Key / 用户可读全站所有 PUBLIC 库;个人组织可随手把库设 PUBLIC → 违规内容广播、难治理P1
3新建 Key allowed_kb_ids 为空且创建接口不支持指定 → 开箱只能读公共库,授权私有库须直接改库P1
4Key 读写不分(读集=写集),无只读/读写分级;scopes 为死字段(无强制)P1
5开发者中心文案"按 key 绑定的组织过滤数据"与实现不符P0
6Key 明文入库、无 hash、无过期;限流 fail-openP2
7组织切换未严格作用域:切到某组织时,自己拥有的 PUBLIC 库仍穿透显示,且带 owner 级编辑/删除,产生"MEMBER 却能编辑自己公开库"的割裂P1

选择模型 Y 后,#2 / #7 因"移除全域公开"而自然消解;#1/#3/#4/#6 由 API Key 授权改造解决;#5 为纯文案。

2目标模型:纯多租户 SaaS 隔离

组织 = 硬边界(租户隔离) 组织 A 的库 ──▶ 仅 A 的成员 / A 的 API Key 可见 组织 B 的库 ──▶ 仅 B 的成员 / B 的 API Key 可见 (无跨组织"全域公开";外部应用通过被授权的 API Key 消费指定组织的库)

2.1 可见性收敛

可见性语义谁可读
PRIVATE私有owner / 组织 OWNER·ADMIN / ACL / 被授权 Key
ORG组织内可见本组织成员 + 本组织 Key
PUBLIC移除(全域公开不再存在;跨组织共享改由 API Key 授权实现)

各主体建库可选可见性:

主体可选
个人组织(单人)仅 PRIVATE
企业组织 OWNER / ADMINPRIVATE / ORG
企业 MEMBER—(无建库/改可见性权限)

2.2 组织切换 = 严格作用域 + 权限联动(修 #7)

  • 切到某组织时,知识库列表只显示该组织的库;不再穿透显示自己在别处的库。
  • 行级"编辑/删除"仍按对该库的真实权限(myPermission),但因列表已锁定当前组织,不会再出现"MEMBER 却见到并能编辑自己个人库"的割裂。
  • 权限必须随组织切换整体联动:切换组织时,前端要重新拉取/重算当前组织角色(OWNER/ADMIN/MEMBER),并让所有受权限门控的 UI 一起刷新 —— 菜单(性能诊断/评测实验室等按当前组织角色显隐)、按钮(创建知识库/编辑/删除/邀请成员/生成 API Key)、以及列表内容,都要以"切换后的组织"重新判定,不能残留上一个组织的状态。
联动实现要点
组织切换器变更 currentOrgId 时:①更新请求头(X-Org-Id);②重新获取该组织下的 myRole 与能力;③触发依赖组织的页面数据与按钮/菜单重渲染(响应式驱动,而非仅切换显示)。避免"切了组织但按钮还按旧组织角色显示"的错位。

3超级管理员定位:纯平台运营方

能力是否保留
拥有 / 发布业务知识库❌ 去掉(内容归各组织;超管的个人内容以普通用户身份建私有库,与"超管"帽子分离)
全平台视图下的"创建组织 / 创建知识库 / 上传"入口❌ 隐藏——切到超管全平台视图(isPlatform)时,这些写入口一律不显示;该视角只做俯视/治理。现状:创建知识库/创建组织按钮未做 isPlatform 门控,待修
日常随意跨组织访问❌ 去掉(现状已需显式破玻璃)
审计式破玻璃(X-Admin-Override + 填原因 + 记 admin_access_audit)✅ 保留——用于排障 / 合规 / 违规内容下架
破玻璃是 SaaS 做合规与内容治理的标配,不能砍:要能下架违规内容,平台方就必须有一条受控、可审计的跨组织通道。"纯隔离"指的是数据按组织硬隔离 + 超管不碰业务内容,而非"超管零跨组织能力"。

4API Key 授权模型

API Key 定位为组织级凭证(服务账号),供外部应用/服务接入。改造目标:最小权限 + 显式授权 + org 真正参与隔离。

4.1 Key 的可配置属性(创建时确定)

属性取值说明
scope_modeORG_ALL(默认) / KB_LIST默认 ORG_ALL=读本组织全部库;KB_LIST=指定 KB 列表(落 allowed_kb_ids,创建时校验归属本组织)
access_levelREAD(本期仅此) / READ_WRITE本期只做 READ(search/answer);READ_WRITE 暂不开放(无写接口),字段保留占位
expires_at日期 / 永不过期到期自动失效

4.2 可读集重定义(org 参与过滤)

// 服务账号可读集(KbAccessGuard,改用 Key 的 org_id 而非 userId)
scope_mode = ORG_ALL  → 本组织(org_id)下所有库 ∪ 本组织 ORG 可见库
scope_mode = KB_LIST  → allowed_kb_ids(已校验属于本组织)
// 移除"无差别并入全站 PUBLIC";写集仅 READ_WRITE 才非空

4.3 安全基线【本期全做】

  • 哈希存储:Key 仅创建时返回一次明文,入库存 hash(如 SHA-256)+ 展示用前缀;鉴权按 hash 比对。
  • 过期时间:支持 expires_at,到期自动失效。
  • 限流 fail-closed:Redis 不可用时按保守阈值拒绝,不再 fail-open 放行。
  • scopes 死字段:以 access_level 表达读/写后,废弃 scopes 以简化模型。

5CareerMate 接入落地

两拨"用户"必须分清
RAGForge 用户(组织成员,管理知识)与 CareerMate 终端用户(CareerMate 自己的账号体系)是两套。RAGForge 不认识 CareerMate 的终端用户。

5.1 访问模型:应用级授权(不是"加入组织",也不是"天然有权限")

CareerMate 终端用户 ──登录──▶ CareerMate 后端 ──(持 1 把 API Key)──▶ RAGForge「求职组织」的库 ▲ 从求职组织签发,授权到 JD/薪资/面试/公司库(只读)
  • CareerMate 后端持一把组织级 API Key,代所有终端用户查询;
  • CareerMate 终端用户无需 RAGForge 账号、无需加入组织 —— 通过 CareerMate 后端间接访问(类比"App 用一把 key 调用云服务,终端用户不各自注册")。

5.2 建一个专门的「求职组织」持有共享数据

新建 TEAM 组织「求职数据」 ├── JD库 / 薪资库 / 面试题库 / 公司库 → PRIVATE(或 ORG),公共参考数据 └── CareerMate API Key(从本组织签发,scope=KB_LIST 授权这几个库,READ)

不放在超管个人组织:超管应是纯运营方,个人组织是单人私有语义,均不适合当"数据提供方"。

约定:谁来建/拥有这个「求职组织」
由一个业务/运营负责人以普通用户账号创建并担任 OWNER —— 不是超管(超管纯治理、不拥有内容),也不是终端用户(平台官方数据不归个人)。该 OWNER 负责:维护公共参考库、签发 CareerMate 的 API Key、管理组织成员。
关键是用哪个账号/角色而非"哪个人":同一自然人可同时持有超管账号(治理)与运营账号(数据组织 OWNER),两顶帽子分离。

5.3 共享参考数据 vs 个人数据(边界)

库性质本期处理
JD / 薪资 / 面试题 / 公司库公共参考(所有求职者通用)✅ 放「求职组织」,一把只读 Key(ORG_ALL)共享
个人简历等每个终端用户私有本期不纳入 RAGForge,由 CareerMate 侧自管(见 §10 D-B 已定)

→ 本期 RAGForge 只承担"公共参考知识"的供给;终端用户个人数据的隔离留待将来按需再设计,不进本期共享组织。

7鉴权链路与前端改造

7.1 后端

  • applyOwnership / validateTargetVisibility:个人组织仅 PRIVATE;团队组织 PRIVATE/ORG;移除任何 PUBLIC 通道。
  • KbAccessGuard:服务账号按 Key 的 org_id + scope_mode 解析可读集;删除"并入全站 PUBLIC";canRead 去掉 isPublic 分支。
  • KB 列表 filterByOrgContext:严格锁定当前组织(去掉 PUBLIC 穿透)。

7.2 前端改造(页面/组件)

⓪ 超管全平台视图(isPlatform) 隐藏一切"创建/写入"入口:创建知识库、创建组织、上传文档等一律不显示(治理视角只读) ① 开发者中心 DeveloperCenter.vue 创建 Key 弹窗:访问范围/可访问库/读写级别/有效期;列表加前缀·级别·到期;修正"按组织过滤"文案 ② 知识库管理 KnowledgeBase.vue 可见性下拉:个人库仅"私有"、团队库"私有/组织内公开";移除"公开"选项 ③ 知识库列表 严格按当前组织显示(切组织=换作用域),消除跨组织穿透 ④ 检索/应答调试台 范围选择器仅列当前组织可见库 ⑤ 平台管理·治理(超管) 破玻璃查看 + 违规内容下架 + 审计(为内容治理保留) ⑥ 组织切换器(全局) 切换即重算 myRole/能力,联动刷新菜单·按钮·列表(见 §2.2)

8迁移与兼容

  • 存量 job 库(现状:owner=超管、在超管个人组织 org 64、PUBLIC):①建「求职数据」组织;②将这 5 个库 org_id 迁至该组织(目前无"换组织"接口,走一次性 SQL);③可见性改 PRIVATE/ORG;④发 CareerMate Key 授权这些库。先建好授权,再收 PUBLIC,避免 CareerMate 中断。
  • 其它存量 PUBLIC 库:非上述用途的一律降级 PRIVATE 或按 owner 组织归位;孤儿/测试库清理。
  • 存量 Key:新建默认 ORG_ALL,但存量迁移为 KB_LIST + 现有 allowed_kb_ids + READ(保留其原有窄范围,避免迁移意外放大权限);在用集成不断。
  • 明文→hash:双写过渡,鉴权先 hash 再回退明文,灰度后删明文列。

10待决策项

D0. 组织模型 已定
采用纯多租户 SaaS 隔离(模型 Y):移除全域公开、超管纯运营方、外部应用走 API Key 授权。
D-A. CareerMate 接入方式 已定
专门「求职组织」持有公共参考库 + 应用级 API Key(KB_LIST 授权);终端用户不加入组织、不需 RAGForge 账号。
D-B. CareerMate 终端用户"个人数据(简历)"隔离 已定
本期不纳入:RAGForge 只提供公共参考库(JD/薪资/面试/公司);个人简历等数据由 CareerMate 侧自管,不进 RAGForge 共享组织。
D-C. API Key 默认 scope_mode 已定
默认 ORG_ALL(Key 读本组织全部库);KB_LIST 作为更细粒度的可选项。CareerMate Key 从「求职组织」签发,ORG_ALL 即覆盖该组织全部共享库。
D-D. 是否开放 READ_WRITE 级 Key 已定
暂不开放写:当前无写接口接受 Key,本期只做 READ。access_level 字段保留占位,将来确有回写需求(如采集入库)再开放并严格限 org + 写集。
D-E. 凭证安全基线 已定
全部做:Key 哈希存储(仅创建时返回明文)+ 过期时间 + 限流 fail-closed。
