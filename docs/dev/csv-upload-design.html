1.背景与目标

当前 CSV 在四道白名单(散传后端 ALLOWED_EXTENSIONS、压缩包 SupportedDocumentTypes、前端 accept、解析器)中全部缺席——前端选不了 .csv,即便绕过去传后端也拒。

CSV 是表格数据,若当纯文本直接分块,会把行列切碎、丢失表头语义、污染向量,检索质量差。

目标:让 CSV(散传 + 压缩包内)按"行即 chunk + 表头前缀"入库,支持记录级语义检索(如"张三是什么职级"、"研发部有谁");聚合统计(平均/求和/分组计数)明确不在本期,见 §10。

2.主流做法对比(为何选行即 chunk)

做法说明适合取舍
① 行即 chunk + 表头
本方案		每行拼成 列名: 值;列名: 值,整行一段;表头拼在每行前。LangChain CSVLoader 同款记录级语义检索做不了跨行聚合统计
② 转 Markdown 表格CSV→markdown 表格再分块小表格(几十行)结构清晰大表格切到中间会丢表头/错位,需每块重复表头
③ 结构化 + NL2SQL / Pandas灌进 SQL/DataFrame,LLM 生成查询去算聚合统计("平均薪资/几人")要引 SQL 引擎 + query 路由,量级大;非向量 RAG 范畴

RAGForge 是向量 RAG 知识引擎(非分析型数据库),务实匹配 = ①,可选叠加 ② 对小表格。本方案取 ①。

3.设计要点

① 白名单四处放行 csv

散传 ALLOWED_EXTENSIONS、压缩包 SupportedDocumentTypes.DOC_EXTENSIONS、前端 accept + EXTENSION_CONTENT_TYPES(csv→text/csv)、散传 MIME 校验加 csv case。

② 新增一步 CSV→行文本转换(核心,唯一新逻辑)

在 DocumentPipelineService.resolveText 里对 text/csv 特判——不走 readRawText 原样喂,而是先解析成"每行带表头"的可读文本,再完全复用现有文本分块 + 向量化 + 检索管道,一行不改下游。

③ CSV 解析用 Apache Commons CSV

新增 commons-csv 依赖(~1 个 jar),稳妥处理引号包裹、值内逗号、值内换行、BOM、编码,避免手写正则踩坑。

4.CSV → 行文本转换

输入 CSV: 姓名,部门,职级,入职 张三,研发,P7,2021-03 李四,产品,P6,2022-08 转换后(喂给现有分块器): 姓名: 张三;部门: 研发;职级: P7;入职: 2021-03 姓名: 李四;部门: 产品;职级: P6;入职: 2022-08

每行一段(空行分隔),表头拼在每行前,保证切开后每个 chunk 仍带列语义。空值列可选择跳过或保留空。

6.决策点(待拍板)

D1 · 分块粒度
推荐:每行 header-prefixed 段落,交现有 size 分块器(多行打包进一个 chunk,省事够用)。备选:严格"一行一 chunk"(需写专用 CsvChunker,稍重)。
D2 · 表头假设
推荐:默认"第一行是表头"。无表头 CSV → 仍当表头 或 用 列1/列2 占位?
D3 · 分隔符
推荐:, 默认 + 自动嗅探 ; / \t(欧洲/Excel 常用 ;)。
D4 · 大表护栏
推荐:设上限(如最多 5 万行 / 解析后总字符上限),超限截断 + log + 写 summary 提示(与压缩包护栏同口径)。阈值待定。
D5 · 超宽单行
推荐:某行拼出超 chunk 大小时按现有分块器正常切(可接受语义略碎)。

7.边界与护栏

  • 编码/BOM:UTF-8 优先,带 BOM 剥除;非 UTF-8 尽力而为,失败回退原文并 log。
  • 畸形行:列数与表头不齐 → 多余列用序号列名、缺列留空,不因单行畸形中断整表。
  • 空表 / 仅表头:无数据行 → 按"无可入库内容"处理(与压缩包空包一致口径)。
  • 超大文件:受散传 50MB 与 D4 行数/字符上限双重约束;压缩包内 CSV 另受单 entry 50MB 约束。
  • 失败友好:解析异常走 ErrorMessages.toUserFriendly 净化为中文,不泄露内部细节(承接 BUG-A 修复口径)。

8.测试用例

单测(本地验证,不提交):带引号、值内逗号、值内换行、BOM、空值、仅表头、无表头、; 分隔、超大截断、畸形行。

云端回归:传真实 CSV → 每行入库成 chunk、表头在、检索"张三 P7"命中;散传 + 压缩包内 CSV 两条路都测。
