# 站内信通知（邀请回执 + 统一未读数 + SSE 实时触达）Playwright 测试用例

> 编制：2026-07-01 · 测试架构师：@guandezhi · 执行方：待定
>
> 依据：《站内信通知优化方案》v1.0（`docs/dev/站内信通知优化方案.html`）
>
> 目标：为方案的 8 个测试域各设计约 10 条 Playwright e2e 用例，覆盖**黄金路径 + 边界值 + 异常注入 + 幂等/并发 + SSE 连接生命周期 + 多副本广播 + 安全越权 + 降级容错**，以"深挖 bug"为目的，不满足于 happy path。**本文只做用例设计，不负责执行。**

## 0. 全局约定

| 项 | 约定 |
|---|---|
| 测试目录 | `frontend/tests/e2e/notification/<域>/`（本地，不入库——遵循"测试文件不提交"团队规则） |
| 命名规范 | `notif-<域号>-<NN>-<short-name>.spec.ts`，NN=01..10 |
| 运行命令 | `npx playwright test tests/e2e/notification --headed --workers=1` |
| 共享 helper | `_helpers/`：登录(A/B/C)、建组织、发/查邀请、SSE 监听封装(`openSse(user)`)、DB 断言(经 admin API 或 SQL) |
| 数据隔离 | 每个用例独立建组织（命名 `notif-<NN>-<ts>`）+ afterAll 清理组织/邀请/通知 |
| 存档 | trace.zip → `frontend/test-results/notification/<域>/` |
| 通过门槛 | 每域 10 条全绿；任一 FAIL 阻断合并 |

### 测试账号（auth-gateway 必须含，prod 必须不存在）

| 账号 | 角色 | 用途 |
|---|---|---|
| `notif_a` / `notif_a` | 组织 Owner | **邀请发起方 A**，回执收件人 |
| `notif_b` / `notif_b` | 普通用户 | **被邀请方 B**，接受/拒绝 |
| `notif_c` / `notif_c` | 普通用户 | 第三方 C，越权/隔离验证 |
| `admin` / `admin` | ADMIN | DB 断言、构造脏数据、注销账号 |

### 被测接口 / 类型

- `POST /api/v1/invitations/{id}/accept`、`POST /api/v1/invitations/{id}/decline`
- `GET /api/v1/notifications`、`GET /api/v1/notifications/unread-count`、`POST /{id}/read`、`POST /read-all`
- `GET /api/v1/notifications/stream`（新增 SSE）
- 通知类型：`ORG_INVITE`（给 B）/ `ORG_INVITE_ACCEPTED` / `ORG_INVITE_DECLINED`（给 A，`userId=inviterUserId`，`refId=invitationId`）

### 断言纪律（贯穿所有用例）

1. **三层断言**：凡涉及回执，必须同时校验 ①DB 行（type/userId/refId/readAt）②`unread-count` 接口 ③UI（角标数字 + 面板文案），三者口径一致。
2. **UI 文案中文化**：失败路径断言 UI 文案，不得出现 `traceId` / Java stack (`at com.ragforge.`) / 裸 `500` / error code / `null`·`NaN`。
3. **SSE 断言可观测**：SSE 用例必须捕获 `EventSource` 收到的原始 event（`page.on` + `window.__sseEvents` 收集），断言事件到达时序与 payload，而非只看角标最终态。
4. **时序断言**：实时类用例要断言"**A 页面不刷新**"（记录 `performance.navigation` / 不触发 `beforeunload`）前提下角标发生变化。

## 域 1 · 接受邀请回执回写（accept → A 侧通知）

覆盖：黄金路径、快照 vs 实时、特殊字符、幂等前置、注销/空值兜底、越权、过期/状态机。

| # | 类型 | 场景 | 步骤要点 | 预期断言 |
|---|---|---|---|---|
| 1-01 | 黄金 | B 接受邀请，A 得到一条回执 | A 邀请 B → B `accept` | DB 新增 1 行 `ORG_INVITE_ACCEPTED`，`userId=A.id`、`refId=invId`、`readAt=null`；A 的 `unread-count` +1；文案含 B 昵称 + 组织名 |
| 1-02 | 边界 | B 昵称含 emoji/CJK/空格 | B 昵称设 `张三🐛 test` 后接受 | 回执文案完整保留，UI 不乱码、不截断错位 |
| 1-03 | 安全 | B 昵称含 XSS `<img src=x onerror>` | 设昵称后接受，A 打开面板 | 文案被转义为纯文本，**无脚本执行**（监听 dialog/console 无触发） |
| 1-04 | 边界 | 超长昵称/组织名（255+） | 边界长度后接受 | 后端不截断报错；UI 省略号处理，hover 全文 |
| 1-05 | **深挖** | 组织在"邀请后、接受前"被改名 | 邀请 → 改组织名 → B 接受 | 明确快照口径：回执用**接受时**的组织名还是邀请时？断言与设计一致，不出现旧名/空名 |
| 1-06 | 兜底 | `inviterUserId` 为 NULL（历史脏数据） | admin 置空该邀请 inviter → B 接受 | 接受**主流程成功**（B 入组织），安全跳过回执，不抛异常、不 500 |
| 1-07 | 兜底 | 发起方 A 已注销 | admin 注销 A → B 接受 | 接受成功；回执 insert 跳过或指向已注销用户不报错；B 侧无异常 |
| 1-08 | 状态机 | 邀请已过期后 accept | 构造 expired 邀请 → B accept | 接口拒绝（`requirePendingForMe` 校验），**不产生回执**，UI 提示"邀请已过期"中文文案 |
| 1-09 | 状态机 | 邀请已是 ACCEPTED 再 accept | 重复调用 accept | 幂等：不重复入组织、**不重复回执**，A 侧仍仅 1 条 |
| 1-10 | 越权 | C 接受本不属于自己的邀请 | C 用 B 的 invId 调 accept | 拒绝（非被邀请人），无回执，返回中文越权提示、无技术 id |

**Bug 深挖清单**：①1-05 快照/实时是最易埋雷点——inviterUserId 是"死字段复活"，组织名同理需确认取值时机；②1-06/1-07 兜底若用 `notificationMapper.insert` 直接抛异常会**回滚整个接受事务**导致 B 无法入组，必须验证"跳过而非抛错"；③1-08/1-09 状态校验要在**回执 insert 之前**，否则过期邀请也会误发回执。

## 域 2 · 拒绝邀请回执回写（decline → A 侧通知，与 accept 对称）

| # | 类型 | 场景 | 步骤要点 | 预期断言 |
|---|---|---|---|---|
| 2-01 | 黄金 | B 拒绝，A 得到拒绝回执 | A 邀请 B → B `decline` | DB 新增 `ORG_INVITE_DECLINED`，`userId=A`；A 角标 +1；文案含"已拒绝" |
| 2-02 | 对称 | 拒绝**不**把 B 加入组织 | B decline 后查 org_members | `org_members` 无 B；仅邀请状态 DECLINED |
| 2-03 | 状态机 | 已 accept 的邀请再 decline | accept 后调 decline | 拒绝/幂等，不产生 DECLINED 回执，状态不回退 |
| 2-04 | 状态机 | 已 decline 再 decline | 连续两次 decline | 幂等：A 侧仅 1 条 DECLINED 回执 |
| 2-05 | 竞态 | 同一邀请 accept 与 decline 并发 | 并发两请求 | 仅一个生效，回执与最终状态一致，**不同时出现** ACCEPTED+DECLINED 两条 |
| 2-06 | 兜底 | decline 时 inviter 已注销 | 同 1-07 | decline 主流程成功，回执安全跳过 |
| 2-07 | 越权 | C decline 他人邀请 | C 用 B 的 invId | 拒绝，无回执 |
| 2-08 | 边界 | 过期邀请 decline | expired → decline | 拒绝，无回执，中文文案 |
| 2-09 | 深挖 | decline 后 A 能否重新邀请 B | decline → A 再次邀请 B | 允许再次邀请，产生新的 ORG_INVITE；旧 DECLINED 回执保留不受影响 |
| 2-10 | 三层 | DECLINED 回执标记已读链路 | A 读该回执 | `readAt` 置值，`unread-count` -1，UI 角标同步 |

**Bug 深挖清单**：①2-05 accept/decline 竞态是并发经典雷区，需 DB 乐观锁/唯一约束保证状态机单向；②2-09 "拒绝后重新邀请"若用 `(refId,type)` 做全局唯一会误拦第二次邀请，要确认幂等键含区分维度。

## 域 3 · 幂等 · 并发 · 事务一致性

覆盖：双击、并发、事务回滚、脏未读防护、重试。

| # | 类型 | 场景 | 步骤要点 | 预期断言 |
|---|---|---|---|---|
| 3-01 | 幂等 | 前端双击 accept（按钮未禁用） | 快速点两次 | A 侧回执**仅 1 条**；org_members 仅 1 行 |
| 3-02 | 并发 | 两并发请求 accept 同一邀请 | `Promise.all` 两 POST | 幂等键 `(refId,type,userId)` 保 1 条；无主键冲突 500 |
| 3-03 | **事务** | 回执 insert 失败 → 整体回滚 | 注入 notification 表异常（admin 制造约束冲突/断连） | accept 事务回滚：**org_members 也不写入**，邀请状态不变；接口返回可重试 |
| 3-04 | **脏未读** | 事务回滚后不得推 SSE / 不加未读 | 同 3-03 + A 开 SSE | A **未收到**推送，`unread-count` 不增（推送必须在 commit 之后） |
| 3-05 | 重试 | 网络重试导致重复 POST accept | 同 idempotency-key 重发 | 结果幂等，A 侧不叠加回执 |
| 3-06 | 并发 | B 对多个不同邀请批量接受 | 5 个组织邀请同时 accept | A/各 inviter 各得 1 条对应回执，无串号（refId 不错配） |
| 3-07 | 并发压力 | 100 封邀请集中接受 | 循环并发 | 回执数 = 邀请数，`unread-count` 精确；无丢失/重复 |
| 3-08 | 隔离 | 事务未提交时其他请求读不到 member | 长事务中并发查询 | 不读到未提交成员（无脏读） |
| 3-09 | 深挖 | 同事务内回执与 member 顺序 | 校验回执 insert 在成员 insert 之后、同一事务 | 二者要么全成功要么全回滚 |
| 3-10 | 幂等键 | 唯一约束覆盖 | 直接 SQL 插重复 `(refId,type,userId)` | DB 层唯一约束拒绝，验证幂等不仅靠应用层"先查后插"（防并发窗口） |

**Bug 深挖清单**：①3-10 "先 select 再 insert"存在并发窗口——两请求都 select 到"不存在"再各插一条，**必须有 DB 唯一约束兜底**，仅应用层判断会漏；②3-03/3-04 是 SSE 设计的核心正确性——"事务提交后才推送"，用注入回滚验证是否会推出脏未读数。

## 域 4 · 统一未读数角标（badge = 待处理邀请 + 未读通知）

| # | 类型 | 场景 | 步骤要点 | 预期断言 |
|---|---|---|---|---|
| 4-01 | 黄金 | 角标 = 邀请数 + 未读通知数 | 构造 A 有 2 待处理邀请 + 3 未读通知 | 角标显示 **5**；`unread-count` 返回 5 |
| 4-02 | 一致性 | 接口与 UI 数字一致 | 任意组合 | UI 角标 === `unread-count` 响应，逐次校验 |
| 4-03 | 递减 | 标记单条通知已读 | 读 1 条 | 角标 -1；重新拉取一致 |
| 4-04 | 递减 | 接受一个邀请 | B 接受后看 B 自己角标 | B 的"待处理邀请"-1，角标相应变化（区分收发视角） |
| 4-05 | 归零 | read-all | 全部已读 | 通知区未读归零；**待处理邀请是否计入 read-all？** 断言语义（邀请需操作而非"已读"） |
| 4-06 | 边界 | 0 未读 | 无任何未读 | 角标隐藏或显示 0（按设计），不显示空红点 |
| 4-07 | 边界 | 99+ 大数显示 | 构造 150 条未读 | 显示 `99+`，不溢出布局 |
| 4-08 | 防护 | 未读数不为负 | 对同一通知重复 read | 角标不出现负数/闪烁到 -1 |
| 4-09 | 并发 | 已读与新通知同时发生 | 读旧的同时来新的（SSE） | 角标 = 净值，无竞态错算 |
| 4-10 | 深挖 | 跨组织统计维度 | A 在多个组织 | 未读数按**用户维度**汇总，切换组织角标不变（除非设计为组织隔离，需断言一致） |

**Bug 深挖清单**：①4-05 "待处理邀请"计入统一未读数，但 read-all 语义上不该把"需要操作的邀请"标记消失——要断言 read-all 只清通知区、邀请区仍在；②4-10 用户级 vs 组织级统计口径若不清会导致切组织角标跳变。

## 域 5 · 分区面板（待处理邀请 / 通知 两区）

| # | 类型 | 场景 | 步骤要点 | 预期断言 |
|---|---|---|---|---|
| 5-01 | 黄金 | 两区正确分类 | A 同时有邀请 + 回执 | 邀请落"待处理邀请"区、回执落"通知"区，不混淆 |
| 5-02 | 交互 | 邀请区可接受/拒绝 | 面板内点接受 | 就地处理，该项移出邀请区；无整页 `reload` |
| 5-03 | 交互 | 通知区只读 + 标记已读 | 点通知 | 仅标记已读，无"接受/拒绝"按钮 |
| 5-04 | 空态 | 无邀请无通知 | 清空 | 显示"暂无消息"占位，非空白/NaN |
| 5-05 | 空态 | 仅邀请 / 仅通知 | 两种单区 | 空的一区显示占位，另一区正常 |
| 5-06 | 边界 | 大量通知滚动/分页 | 200 条通知 | 分页或懒加载正常，不卡死，滚动到底有终止态 |
| 5-07 | 展示 | 相对时间格式 | 制造不同时间通知 | "刚刚/x分钟前/日期"正确，无 `Invalid Date` |
| 5-08 | 深挖 | 去掉 reload 后组织切换器同步 | 面板内接受邀请 | 侧栏组织列表/切换器**无刷新即更新**新组织，无需 F5 |
| 5-09 | 安全 | 通知 content 渲染转义 | 注入 HTML 的通知 | 纯文本渲染，无 DOM 注入 |
| 5-10 | 交互 | 面板打开是否自动已读 | 打开面板 | 按设计：打开**不**自动清未读（需点击/或有"全部已读"按钮），断言与设计一致 |

**Bug 深挖清单**：①5-08 方案明确要去掉 `window.location.reload()`，接受邀请后组织态如何无刷新更新是回归高危点；②5-10 "打开面板即已读"会让用户漏看——需确认是否为有意设计。

## 域 6 · SSE 实时推送（黄金路径 + 心跳 + 超时 + 重连）

| # | 类型 | 场景 | 步骤要点 | 预期断言 |
|---|---|---|---|---|
| 6-01 | 黄金 | B 接受 → A 免刷新秒级 +1 | A 挂 SSE 静置 → B accept | **A 页面无导航**，≤2s 内角标 +1；捕获到 1 个 SSE 事件 |
| 6-02 | 格式 | SSE 事件结构 | 捕获原始 event | `event`/`data` 字段规范，payload 含 unread-count 或触发刷新的标识 |
| 6-03 | 心跳 | 25s 心跳保活 | 静置 90s | 连接不断（收到 ≥3 次心跳/ping），角标不异常 |
| 6-04 | 超时 | SseEmitter 30min 到期 | 模拟/缩短 emitter 超时 | 连接正常结束 → `EventSource` **自动重连**，业务不中断 |
| 6-05 | 重连 | 断网后自动重连 | offline→online | `EventSource` 自动重连成功 |
| 6-06 | **对齐** | 重连后拉一次对齐 | 断网期间 B 发生 3 次操作 → A 恢复 | 重连后前端主动拉 `unread-count`，**补齐断网期间遗漏**，最终数字正确不丢 |
| 6-07 | 幂等 | 抖动多次重连不重复计数 | 快速 offline/online 多次 | 角标不因重连叠加、不重复 +1 |
| 6-08 | 恢复 | 服务端重启后重连 | 重启 api | 前端重连并对齐，无需用户刷新 |
| 6-09 | 时序 | 推送与接口最终一致 | 混合 SSE 推送 + 手动拉取 | 二者收敛到同一未读数（SSE 为增强，接口为准） |
| 6-10 | 深挖 | 推送到达但用户已读该通知 | A 在别标签读了，SSE 又推旧事件 | 不出现"已读又变未读"回跳；以服务端未读数为准 |

**Bug 深挖清单**：①6-06 是防丢消息的命门——SSE 不保证断连期间不丢，**必须靠"重连后拉取对齐"兜底**，否则断网即漏；②6-07 重连叠加计数是常见实现 bug；③6-10 推送携带"增量 +1"而非"最新未读数"时，乱序/重复会导致错算，建议推"最新值"而非"增量"。

## 域 7 · 多标签页 · 多副本广播 · 降级

| # | 类型 | 场景 | 步骤要点 | 预期断言 |
|---|---|---|---|---|
| 7-01 | 多标签 | 同用户多标签都收到推送 | A 开 2 个标签挂 SSE → B accept | 两标签角标都 +1 |
| 7-02 | 多标签 | 一标签已读，其他标签同步 | 标签1 read → 看标签2 | 标签2 角标同步递减（推 read 事件 或 各自对齐），断言不出现两标签数字打架 |
| 7-03 | **多副本** | 连接与推送源分属不同副本 | A 连副本1（固定路由）、B 的 accept 落副本2 | 经 **Redis Pub/Sub** 广播，A 仍秒级收到；关掉 Redis 广播则收不到（反证链路） |
| 7-04 | 副本 | 重连落到不同副本 | 重连后路由到副本3 | 新副本持有 emitter，推送正常 |
| 7-05 | 降级 | Redis 不可用 | 停 Redis | 推送失败**不影响** accept 主流程；A 靠刷新/降级仍能看到（不 500） |
| 7-06 | 降级 | SSE 被代理断开 → 轮询 fallback | 模拟 Nginx 断 SSE | 前端降级到轮询 `unread-count`（若实现），或至少不报错、刷新可见 |
| 7-07 | 泄漏 | 关标签 onCompletion 移除 emitter | 开/关标签多次 | 服务端 emitter map 不泄漏（数量回落），无内存增长 |
| 7-08 | 压力 | 大量并发 SSE 连接 | N 个用户同时连 | 连接稳定，心跳正常，emitter 管理无崩溃 |
| 7-09 | 广播 | Redis 消息重复投递幂等 | 模拟重复 pub | 前端不重复 +1（配合 6-07/6-10 以"最新值"消费） |
| 7-10 | 扩缩容 | 副本缩容断连迁移 | kill 一个 api pod | 该副本上的连接前端自动重连到存活副本 |

**Bug 深挖清单**：①7-03 是"api 3 副本"下最核心的正确性——不接 Redis 广播时跨副本必然收不到，用例要能**反证**（关广播→收不到，开广播→收到）；②7-07 emitter 泄漏是长连接服务隐性 OOM 源，必须验 onCompletion/onTimeout/onError 三处都清理；③7-02 多标签已读同步若无跨标签机制会长期数字不一致。

## 域 8 · 权限 · 鉴权 · 安全 · 异常边界

| # | 类型 | 场景 | 步骤要点 | 预期断言 |
|---|---|---|---|---|
| 8-01 | 鉴权 | SSE 未带 JWT | 无 token 连 `/stream` | 401 拒绝建连，不泄漏数据 |
| 8-02 | 鉴权 | 过期/伪造 JWT 连 SSE | 篡改 token | 拒绝或建连后立即断开，无推送 |
| 8-03 | 隔离 | A 的通知 B 拿不到 | B 调 `GET /notifications` | 仅返回 B 自己的，看不到 A 的回执 |
| 8-04 | 越权 | 越权标记他人通知已读 | B 用 A 的 notificationId 调 read | 拒绝，A 的 `readAt` 不变 |
| 8-05 | 越权 | SSE 推送不串户 | A、C 同时在线，B accept A 的邀请 | 只有 A 收到推送，**C 收不到** |
| 8-06 | 边界 | 不存在的 notificationId 标记已读 | 随机 id read | 404 友好中文文案，无 stack trace |
| 8-07 | 边界 | 伪造 refId/invitationId accept | 不存在 invId | 拒绝，中文提示，不产生回执 |
| 8-08 | 安全 | 通知 content XSS 端到端 | 注入脚本类内容 | 列表与角标 tooltip 均转义，无执行 |
| 8-09 | 边界 | 超长 content/title | 边界长度 | 后端不报错、UI 截断 + 全文可见，无布局崩 |
| 8-10 | 会话 | 登出后未读数与 SSE 清理 | A 登出 | SSE 连接关闭，角标清空；重新登录重新建连并对齐 |

**Bug 深挖清单**：①8-05 SSE 串户是长连接鉴权最危险的泄漏——emitter 必须严格按 userId 隔离，Redis 广播 payload 不能被错误副本投给别的用户；②8-10 登出未断 SSE 会导致"僵尸连接"继续接收，既泄漏又占资源；③8-03/8-04 通知查询/标记必须带 `userId=当前用户` 的强过滤，不能只按 id。
