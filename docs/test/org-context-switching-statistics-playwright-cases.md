# 组织切换联动与统计隔离 Playwright 测试用例

> 编制：2026-07-02  
> 目标：系统性覆盖 RAGForge 中所有会受“当前组织”影响的页面、tab、统计卡片、列表、操作记录和详情页，验证组织切换后数据会刷新、不会串组织、不会被旧请求覆盖。

## 1. 背景与测试原则

当前组织上下文由左侧 `OrgSwitcher` 全局控制：

- 普通组织：`localStorage.ragforge.currentOrgId = <orgId>`，请求拦截器注入 `X-Org-Id`。
- 全平台视图：`localStorage.ragforge.currentOrgId = platform`，请求拦截器注入 `X-Admin-Override: true`。
- 个人组织：也是后端真实组织，不再用空 org 概念。
- 组织切换器当前实现会 `window.location.reload()`，但部分页面也有 `watch(currentOrgId, load)`，测试要同时防止“无刷新更新缺失”和“旧请求覆盖新组织数据”。

统一断言纪律：

1. 组织 O1 / O2 / 个人组织 / 平台视图数据必须可区分，测试数据不要相同。
2. 每个组织下至少构造不同的知识库、文档、评测数据、模型调用成本、API key、组织成员和操作记录。
3. 切换组织后，所有当前页面可见统计、列表、详情入口必须与新组织一致。
4. 不允许出现上一组织的名称、知识库、文档、成员、API key、评测结果、成本排行或操作记录残留。
5. 切换过程要监听接口请求，验证新请求带正确 `X-Org-Id` 或平台破玻璃 header。
6. 快速连续切换 O1 → O2 → O1 时，最终页面只能展示最后一次选中的组织数据，不能被慢返回的旧请求覆盖。
7. 用户级数据，例如账号设置、我的组织列表、通知未读总数，如产品定义为用户维度，不应随组织切换错误变化。

|---|---|---|

| 评测实验室 `/eval` | 题目管理、批量导入、Quick Start、从搜索保存题目 | 候选知识库、chunk、数据集必须属于当前组织 |
| 质量看板 `/evaluation/quality` | KPI、趋势、异常、按知识库排行、最差案例 | 必须按当前组织刷新 |

| 质量案例详情 `/evaluation/quality/case/:id` | 评分、Query/答案、命中片段、reasoning | case 必须属于当前组织；切换后不可打开旧组织 case |

| 组织管理 `/orgs/manage` | 概览、成员、邀请、组织知识库、危险区 | 必须绑定当前组织，切换组织后全部刷新 |

## 2.1 当前实现口径与待统一风险

下面这些点不是测试细节，而是验收口径风险。写自动化前必须先确认产品预期，否则会出现同一功能互斥断言。

| 风险点 | 当前代码核对结论 | 测试要求 |
|---|---|---|
| PUBLIC 知识库口径 | 现有测试文档存在冲突：有的按 PUBLIC 全局可读，有的按“移除 PUBLIC 全局放行”设计；当前 `/eval/*` 仍会把 `visibility=PUBLIC` 纳入 scope | 增加 `ORG-PUB-*` 统一验收用例，先定口径再测 |
| 无 `X-Org-Id` 口径 | `/metrics/dashboard`、`/models/cost/*`、`/evaluation/quality/*` 无 org 时偏空 scope；`/eval/*`、部分 KB 权限接口无 org 时不一定空 | 增加 `ORG-NOCTX-*`，逐接口固定预期 |
| 搜索 `/search` | JWT 用户搜索按 KB 可读权限，不严格按当前 `X-Org-Id` 收窄；`X-Org-Id` 主要影响 retrieval log/cost 归属 | 测“候选 KB 是否当前组织”和“日志/成本归属是否当前组织”，不要误把所有可读 KB 都判 bug |
| 应答 `/answer` | 前端 `AnswerPlayground` 使用原生 `fetch`，不会走 axios 请求拦截器，因此不自动带 `X-Org-Id` / `X-Admin-Override` | 必须测请求头和归属；这是高优先疑似缺陷 |
| 文档 / KB 详情 | 多数接口按 `KbAccessGuard` 可读/可写鉴权，不额外要求 `kb.org_id == currentOrgId` | 如果 UI 视角要求组织隔离，必须在前端切组织时清空/离开旧详情 |
| 质量 case 详情 | 列表按当前 org 的 KB 集合过滤；详情只按 case 中 KB 是否可读判断 | 必须测“从 B 组织打开 A case URL”是否符合产品预期 |
| 抽样配置 | `/evaluation/quality/sampling/*` 当前是 ADMIN 全局配置，不按 org 过滤 | UI 如显示在组织页面，要明确是全局配置还是组织配置 |
| Golden Set enabled count | 当前是全平台 enabled count，不按 org 过滤 | 质量看板显示时需明确是否应全局或组织级 |
| 平台破玻璃审计 | 平台 dashboard / governance 操作会写 `admin_access_audit`，前端暂无审计记录页面 | 平台视图测试要额外查审计表或 admin API |
| 多 tab 组织上下文 | 当前组织存在 localStorage，切换会影响后续请求；两个 tab 同时打开不同组织存在串上下文风险 | 增加双 tab 专项 |

## 3. 不应随组织切换错误变化的功能

| 页面 / 功能 | 预期 |
|---|---|
| 账号设置 `/account`：个人设置、安全中心 | 用户级，不按组织切换清空或串数据 |
| 我的组织 `/orgs` | 用户加入的组织全集，不是当前组织过滤结果；当前组织变化不应少组织 |
| 通知铃铛 | 统一未读数当前定义为用户维度；切换组织不应把用户级未读误当组织级清零 |
| 登录 / 注册 / 重置密码 / 403 | 不依赖当前组织统计 |
| `/api-gateway` | 当前路由重定向到 `/api`，不单独覆盖旧页面 |

## 4. 测试数据设计

准备 3 个组织：

- `O-PERSONAL`：测试用户个人组织。
- `O-TEAM-A`：团队组织 A。
- `O-TEAM-B`：团队组织 B。

每个组织下使用强区分数据：

| 数据类型 | O-TEAM-A | O-TEAM-B |
|---|---|---|
| 知识库 | `orgctx-a-kb-*`，2 个库 | `orgctx-b-kb-*`，1 个库 |
| 文档 | A: 3 个文档，chunk 数与 B 不同 | B: 1 个文档 |
| 检索调用 | A: 5 次成功、1 次零结果 | B: 2 次成功、0 次零结果 |
| 评测数据集 | A: 2 个 dataset，题目数 3/5 | B: 1 个 dataset，题目数 2 |
| 评测实验 | A: Top3/MRR/latency 固定为一组 | B: 固定为另一组 |
| 质量结果 | A: 通过率、平均分、异常数与 B 不同 | B: 明显不同 |
| 模型成本 | A: embedding / rerank / LLM 都有费用 | B: 只构造 embedding 或费用更低 |
| API key | A: `orgctx-a-key-*` | B: `orgctx-b-key-*` |
| 成员 | A: Owner + Member B | B: Owner + Member C |
| 操作记录 | A: 上传/检索/评测/邀请 | B: 创建 key/检索/删除文档 |

## 5. 专项测试用例

### 域 A：全局组织切换与请求头

| # | 场景 | 步骤 | 预期 |
|---|---|---|---|
| OCT-A01 | 切换团队组织后所有 API 使用新 `X-Org-Id` | 登录 → 选 O-TEAM-A → 打开驾驶舱 → 选 O-TEAM-B | 切换后页面请求全部带 O-TEAM-B 的 `X-Org-Id`；不再带 O-TEAM-A |
| OCT-A02 | 个人组织切换 | O-TEAM-A → 个人组织 → 打开知识库/驾驶舱 | 展示个人组织数据；无团队组织私有库、成员和操作记录 |
| OCT-A03 | 平台视图破玻璃 | 管理员切到平台视图 → 打开驾驶舱/模型成本/知识库 | 请求带 `X-Admin-Override`；展示平台聚合或平台管理态；普通用户无该入口 |
| OCT-A04 | 快速连续切换抗旧请求覆盖 | 拦截 O-TEAM-A 指标请求延迟 → 快速切 O-TEAM-B | 最终页面只显示 O-TEAM-B；迟到的 O-TEAM-A 响应不能覆盖 UI |
| OCT-A05 | 切换后不保留旧组织空态/加载态 | O-TEAM-A 有数据，O-TEAM-B 为空 | 切换到 B 后显示 B 的空态，不显示 A 的历史数据 |
| OCT-A06 | 无 `X-Org-Id` 接口口径固定 | 清空 localStorage currentOrgId，分别请求 dashboard/cost/quality/eval/kb/search | 各接口行为与产品口径一致；不得意外泄漏全平台统计 |
| OCT-A07 | PUBLIC 可见性口径固定 | A 创建 PUBLIC/ORG/PRIVATE 三类库，B 切组织访问 | PUBLIC 是否跨组织可见、是否计入 dashboard/eval/quality/search 按统一口径断言 |
| OCT-A08 | 双 tab 组织上下文隔离 | tab1 切 A，tab2 切 B，分别操作列表/搜索/成本 | localStorage 变化后的请求头、缓存和 UI 不互相污染；如设计为全局生效，要有明确刷新/提示 |
| OCT-A09 | 当前组织失效回退 | 用户停留 A，被管理员移出 A 或 A 被删除 | 旧 orgId 请求 403/404 后，组织列表刷新并回退可用组织；不回退平台视图 |

### 域 B：驾驶舱统计与操作记录

| # | 场景 | 步骤 | 预期 |
|---|---|---|---|
| OCT-B01 | 资产规模按组织刷新 | O-TEAM-A / O-TEAM-B 分别构造不同 kb/doc/chunk | 切换后资产规模、文档数、知识库数、chunk 数准确匹配当前组织 |
| OCT-B02 | 检索质量按组织刷新 | A/B 构造不同零结果率、平均召回、rerank 分、改写率 | 切换后检索质量卡片与接口 `/metrics/dashboard` 一致 |
| OCT-B03 | 运行健康按组织刷新 | A/B 构造不同 P50/P95、成功率、请求数 | 切换后运行健康卡片准确变化 |
| OCT-B04 | 成本消耗按组织刷新 | A/B 构造不同 token 与 embedding/rerank/LLM 费用 | 切换后总费用、Token、分项费用准确变化 |
| OCT-B05 | 检索趋势按组织刷新 | A/B 构造近 7 天趋势不同 | 趋势柱状图、总请求、成功率、日期点准确切换 |
| OCT-B06 | 入库处理健康度按组织刷新 | A/B 构造 completed/processing/queued/failed 不同 | 分段条和失败提示只反映当前组织 |
| OCT-B07 | 组织成员按组织刷新 | A/B 成员数量和角色不同 | 成员概览、成员列表、Owner/Admin/Member 数准确；个人/平台态按设计隐藏 |
| OCT-B08 | 最近操作按组织隔离 | A/B 构造不同 recentActivities | 切换后“最近操作”只出现当前组织操作；不得出现另一组织的文案、资源名或时间线 |
| OCT-B09 | 操作记录与统计联动 | 在 O-TEAM-A 上传文档并检索 | A 的最近操作增加，资产/趋势同步变化；切到 B 不变化 |
| OCT-B10 | 驾驶舱入口跳转保持组织上下文 | 从 A 的失败文档提示跳知识库，从成本卡跳模型成本 | 目标页仍是 A 组织数据；切到 B 后同入口显示 B 数据 |
| OCT-B11 | 最近操作缓存 key 不串组织 | 10 秒内 A/B 来回切换驾驶舱 | `recentActivities` 使用 org 级缓存；A/B 不复用同一缓存 |
| OCT-B12 | 平台视图最近操作与审计 | ADMIN 切平台视图打开驾驶舱 | 最近操作为平台聚合；请求带破玻璃 header；`admin_access_audit` 新增记录 |
| OCT-B13 | 统计 join 膨胀哨兵 | 构造同一 KB 多文档、多 chunk、多检索日志 | 资产、趋势、成本求和不因 join 重复放大 |

### 域 C：知识库、文档、上传、详情

| # | 场景 | 步骤 | 预期 |
|---|---|---|---|
| OCT-C01 | 知识库列表随组织刷新 | A/B 创建不同私有库和组织可见库 | `/knowledge` 切换后列表只含当前组织可访问库；公开库按设计可见但标识清楚 |
| OCT-C02 | 知识库统计列准确 | A/B 文档数、chunk 数不同 | 列表中的文档数、chunk 数、状态与当前组织数据一致 |
| OCT-C03 | 创建知识库默认归属正确 | 切到 O-TEAM-B → 打开创建 | 默认归属或可选归属与当前用户可管理组织一致；创建后出现在 B，不出现在 A |
| OCT-C04 | 编辑可见性不串组织 | A 库与 B 库同名 | 在 A 编辑只影响 A；切到 B 同名库保持原状态 |
| OCT-C05 | 上传向导可写库刷新 | A/B 可写库不同 | `/uploads/wizard` 切换后可选库列表准确；不可向无权限组织上传 |
| OCT-C06 | 文档列表路由鉴权 | 在 A 文档列表页切到 B | 旧 A 私有文档不应继续显示；应刷新、拒绝或引导选择 B 的库 |
| OCT-C07 | 文档详情组织隔离 | 打开 A 私有文档详情 → 切 B 后刷新 | 不泄漏 A 文档元信息、chunk、清洗指标；返回 403/404 或离开详情 |
| OCT-C08 | 重处理/重切分操作归属 | 在 A 文档详情执行重处理 | A 的入库健康度和操作记录变化；B 不变化 |

### 域 D：检索调试台与应答调试台

| # | 场景 | 步骤 | 预期 |
|---|---|---|---|
| OCT-D01 | 检索调试台知识库候选刷新 | A/B 构造不同 KB | `/debug` 切换后 KB 下拉只展示当前组织可访问库 |
| OCT-D02 | 文档筛选随 KB/组织刷新 | 选 A KB 加载文档 → 切 B | 文档候选清空或刷新为 B；不能保留 A 文档 |
| OCT-D03 | 检索结果不串组织 | A/B 用同 query 返回不同命中文档 | 切换组织后结果引用只来自当前组织 |
| OCT-D04 | 对比模式统计准确 | A/B 分别执行 hybrid/vector/keyword 对比 | 耗时、结果数、top score 只对应当前组织结果 |
| OCT-D05 | 保存到评测集候选刷新 | 在 `/debug` 打开保存案例 modal | dataset 下拉只包含当前组织评测数据集 |
| OCT-D06 | 应答调试台 KB 与引用刷新 | `/answer` 切 A/B 后分别提问 | 可选 KB、答案引用、事件流水均来自当前组织 |
| OCT-D07 | 应答/检索成本归属 | 在 A 执行 answer/search | A 驾驶舱和模型成本增加；B 不增加 |

## 6. 每个用例必须记录的证据

1. 切换前当前组织名称和 orgId。
2. 切换后当前组织名称和 orgId。
3. Playwright 捕获的关键 API 请求 headers：`X-Org-Id` / `X-Admin-Override`。
4. 页面可见统计值截图或 DOM 文本。
5. 后端接口响应中的关键字段快照。
6. 组织 A/B 的对照数据表。
7. 失败时 trace.zip、接口响应和页面截图。

## 7. 高风险缺口

1. 驾驶舱当前靠整页 reload 触发刷新，若未来去掉 reload，需要补 `currentOrgId` watcher 或路由级重载测试。
2. 质量案例详情、文档详情、实验详情这类“带 id 的详情页”最容易在切换组织后继续展示旧组织数据，必须重点测。
3. 质量看板使用 query/sessionStorage 保存筛选条件，跨组织切换时容易沿用旧组织 `kbId` 或旧 case query。
4. 检索调试台和应答调试台的结果区如果不在组织切换时清空，容易短暂展示旧组织引用。
5. 模型管理 tab 是“平台配置 + 组织成本字段”的混合页面，不能简单认为全页面都是平台级。
6. API key 和 MCP 是外部访问边界，必须验证 key 绑定组织后的真实调用隔离，而不只是 UI 列表。
7. `AnswerPlayground` 不走 axios 拦截器，是当前组织归属最明确的高风险点。
8. `/search`、`/answer`、文档详情、质量 case 详情存在“KB 权限口径”和“当前组织视角口径”差异，必须先定产品口径再写断言。
9. 已有测试文档中 PUBLIC 和无 `X-Org-Id` 行为存在互斥预期，本专项要作为统一口径的收敛文档。

## 8. 与现有测试文档的关系

本文件不是替代已有文档，而是补“组织切换联动 + 统计准确性 + 操作记录准确性”的总入口：

- `org-permission-test-plan-V2.md`：已有组织生命周期、成员、KB、驾驶舱指标、检索成本归属。
- `org-view-test-plan-V1.md`：已有质量看板、模型成本、驾驶舱、知识库、检索、应答、评测、开发者中心、性能诊断的组织视角覆盖。
- `api-key-authz-testcases.md`：已有 API key/MCP/REST 多租户授权覆盖。
- `notification-invite-sse-playwright-cases.md`：已有通知、邀请、未读数和组织切换器联动覆盖。

新增自动化时优先复用这些文档里已有 seed 和 helper；本文件负责补齐跨页面、跨 tab、切换时序、统计求和和口径冲突。
