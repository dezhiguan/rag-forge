权限重构方案：从「按平台控权」→「组织自治」

RAGForge · 多组织上线后的权限模型重设计 · 供架构师审核
⚠ 模型前提：Claude Code 式「一切皆组织」
不再有"个人空间(org_id=null)"。每个用户注册即拥有一个自己的组织（Individual 类型、单人、你是 OWNER）；企业是 Team 类型（多成员）。当前代码仍是 GitHub 式，需先做模型迁移（见落地方案 P0）。
一把判断尺：每个能力只问一句 —— 它是横跨整个平台的，还是只作用于某一个组织自己的资源的？
横跨平台 → 必须超管（下放=把全平台交出去）；只作用于本组织 → 可下放给该组织的 OWNER/ADMIN。

一、角色模型（三维度，统一到"组织"）

权限不再分"个人 vs 企业"两条轨，统一为：平台角色(超管) × 组织类型(Individual/Team) × 组织角色(OWNER/ADMIN/MEMBER)。「个人组织」= 成员只有你、你是 OWNER 的 Individual 组织，权限与企业 OWNER 在各自组织里一致，只是没有别的成员。

超超管
平台角色 = ADMIN（正交维度）。治理整个平台，跨组织（破玻璃+审计）。
企企业超管
Team 组织的 OWNER/ADMIN。在本组织内是"小超管"。
员普通员工
Team 组织的 MEMBER。只"用"不"管"。
个个人组织
Individual 组织（单人，你=OWNER）。≈ 单人版企业超管。

三、最大的设计债：两个 tab 各是"两半"

🔒 平台那半（超管）
  • 模型选型、Provider 凭证、模型注册/路由
  • 平台总账单、跨组织成本对账
  • 平台级网关 / 全局 API 配置
🟢 组织/个人那半（可下放）
  • 看本组织/个人的用量与成本（不是改配置）
  • 管本组织/个人 scope 的 API key
  • 让企业自己的 Agent/应用按组织上下文接入
现状把这两半整块锁在超管 → 企业看不到自己花了多少钱、管不了自己的 key，是从"组织自治"角度最该补的缺口。

四、落地方案（分阶段）

  1. 模型迁移：GitHub 式 → Claude Code 式（一切皆组织）P0·前置·不可回退
    organizations 加 type(INDIVIDUAL/TEAM)；注册时为每个用户建一个 Individual 组织；存量"个人库"(org_id=null) 迁移到各自 Individual 组织（回填 org_id）；KbAccessGuard 去掉 owner_user_id 个人分支、统一走组织判定；前端 useOrg 去掉合成的 id:null PERSONAL，改为后端返回的真实 Individual 组织。是 DB 迁移 + 多处改造，须先做。
  2. 权限判定升级为"双维度"P1·地基
    前端 canAccessRoute 在平台角色之外，叠加当前组织上下文 + 组织角色（OWNER/ADMIN/MEMBER）。后端按 X-Org-Id 解析组织角色，授予对应 scope。B 桶(性能/评测/质量/成员/设置)对企业超管在组织内放开。
  3. 导航与页面"上下文感知"P1
    切到不同组织时，导航与每页数据范围随之变（个人=自己、组织=本组织、全平台=超管破玻璃）。员工只看到"用+只读"。
  4. 「成本」拆出组织/个人视图P2
    成本中心拆为：模型配置(超管) + 用量/账单(按 org_id/个人聚合，下放)。依赖用量计量带 org 归属（与 retrieval_logs.org_id 一致口径）。
  5. 「API key」拆出组织/个人 scopeP2
    api_keys 增加归属（org_id / owner_user_id）+ 作用域；企业超管管本组织 key，个人管个人 key，平台级仍超管。
  6. 超管专属域收口 + 审计P3
    模型配置/SYSTEM库/平台总账/封号/全局开关 明确仅超管，且高危走破玻璃+审计；企业侧永远够不到这几样。
一句话定调：一切皆组织后，权限只看「平台角色(超管) × 组织角色(OWNER/ADMIN/MEMBER)」。除"模型配置、平台聚合/跨组织、平台总账、SYSTEM/中间件、平台授权"铁定归超管，其余全部按组织下放 —— 你在自己 Individual 组织里就是 OWNER（小超管），企业 OWNER 同理，都只够不到平台级那几样。
