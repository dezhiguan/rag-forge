1. 背景：V4 体检结论速览

在过去 24 小时的产品 + RAG 用户视角联合审视中，我们形成了以下判断：

  • 底座扎实：Spring Boot 3.2 + PG/pgvector + ES + RocketMQ + 统一 RetrievalService + Flyway + Docker Compose + MCP，已具备企业级骨架。
  • 身份与多租户已收口（V9–V12）：tenant_id、kb_acl、JWT/JWKS、SERVICE_ACCOUNT、retrieval_logs 审计扩展。
  • 仍欠的五块：① 数据清洗缺失；② 分块只有字符滑窗；③ 没有答案侧产品形态；④ 文件存本机磁盘，不可多实例；⑤ 多模态文档处理（图、表、扫描件）整体塌方。
本文档的目标不是推倒 V4，而是沿着 V4 的统一抽象（RetrievalService / pipeline 三件套 / RagAuthContext）顺势扩。 新能力都以「可插拔策略」形式落入既有抽象，而不是新建一条平行链路。

2. V5 目标与产品定位修正

2.1 一句话目标

在不破坏「检索基础设施」定位的前提下，把 RAGForge 升级为 "基础设施 + 可选应答层" 的企业级 RAG 平台，覆盖 「多源接入 → 数据清洗 → 多策略分块 → 多模态索引 → 混合检索 → 可选 LLM 应答」全链路。

2.2 产品定位修正

维度V4 定位V5 定位
核心产物chunks + scores + metadata + latencychunks 默认输出；answer + citations 作为可选开关
对外形态检索 API + 管理后台检索 API + 应答 API + MCP + 嵌入式 Chat-with-Citation 组件
边界口径"不做聊天产品""不强制聊天；提供应答能力，但应答是可关闭、可替换、可审计的"
关键设计原则：Answer-as-LLM 是 opt-in 而非 opt-out。 租户可在 KB 级配置 answer_mode = OFF / PREVIEW / ON，默认 OFF，保持与 V4 一致。

4. 能力 1：数据清洗管道（Cleaner）NEW

4.1 为什么必须做

当前链路：Tika 解析 → 直接送 Chunker。这导致：

  • PDF 解析出的页眉/页脚/页码/水印 → 进入 chunk → 污染向量空间（同一份页脚被 reranker 当成"高频但无信息"误判）。
  • Word 留下的 、零宽字符、不可见控制符 → ES tokenizer 不一致。
  • 合同/简历里 PII（手机/身份证/邮箱）原样入库 → 合规风险。

4.2 设计：分层 + 可配置 + 可审计

Cleaner 接口（SPI）：

  CleanResult clean(RawText raw, CleanProfile profile)

四层流水线：

  L1 Normalize    ── unicode 归一化 / 去控制符 / 换行收敛 / 全半角统一
  L2 Denoise      ── 页眉页脚识别（基于位置 + 重复度）/ 水印 / 目录 TOC
  L3 PII Mask     ── 手机/身份证/邮箱/银行卡 → 哈希或*替换；保留长度
  L4 LLM Rewrite  ── 可选；对扫描件 OCR 错字、断行错误做 LLM 兜底纠错
                     仅在 profile.llmAssist = true 且文档置信度 < 0.7 时触发

输出：CleanResult { cleanedText, removedRegions[], piiMap, llmTokensUsed }

4.3 配置粒度

层级配置项默认
租户全局 PII 策略（脱敏 / 哈希 / 拒绝入库）脱敏
知识库启用层 L1–L4 开关、L4 模型选择L1+L2+L3 开
文档支持「跳过清洗」白名单（合同原文）不跳过

4.4 可观测性

  • 每文档保存 clean_report：删除区域、删除字符数、PII 命中数、LLM token 消耗。
  • 新增 "清洗对比" 页：左原文 + 右清洗后 + 高亮 diff，供运营审计。
验收：取 50 份 PDF 作 ground truth，清洗后 chunk 重复率应下降 ≥ 40%， 召回精度（Top1）提升 ≥ 8%。

5. 能力 2：多策略分块（Chunker Family）REWRITE

5.1 当前问题

V4 只有 固定字符窗口，对结构化文档（Markdown / 论文 / 合同 / 财报）召回精度差， 且对用户不可见、不可调。

5.2 五种策略

策略适用场景关键参数实现路线
FIXED_WINDOWKEEP 纯文本、低结构 chunkSize, overlap 保留现有实现，作为兜底
RECURSIVENEW 通用文本（默认） separators[], chunkSize, overlap 按 段落 → 句号 → 逗号 → 字符 递归
MARKDOWN_HEADINGNEW 技术文档、Wiki、README maxLevel, mergeBelow 按 H1/H2/H3 切，保留标题路径作为 chunk metadata
SEMANTICNEW 论文、长文、知识科普 simThreshold, minLen, maxLen 句嵌入 + 相邻余弦相似度，低于阈值即切
TABLE_AWARENEW 财报、合同、产品规格 tablePolicy(WHOLE/ROW), captionRange 识别表格区域整块/按行切，附上下文标题

5.3 抽象设计

public interface ChunkerStrategy {
  String name();
  boolean supports(DocumentMeta meta);
  List<Chunk> split(CleanedText text, ChunkParams params);
}

// 在 KB 上配置默认策略 + 兜底链：
// chunkerProfile: [MARKDOWN_HEADING, SEMANTIC, RECURSIVE]
// 第一个 supports() = true 的执行；否则 fallback。

5.4 配套：分块对比试验

在 EvaluationLab 内新增 「分块 A/B 试验」： 同一文档、同一评测集，跑 N 种策略，对比 Top1/Top3/MRR + 平均 chunk 长度 + 总 chunk 数。 让用户用数据选策略，而不是凭感觉。

5.5 数据兼容

  • document_chunks 增加 chunker_strategy、chunker_params_json、heading_path 字段。
  • 重切分能力：文档级"重新分块"按钮，旧 chunks 软删除（保留 30 天，供回滚）。
权衡：SEMANTIC 分块需要额外 embedding 调用，单文档处理时长增加 30–60%。 建议默认 RECURSIVE，SEMANTIC 作为高级选项，按租户配额计费。

6. 能力 3：Answer-as-LLM 应答层NEW

6.1 边界声明（重要）

引入应答层不等于把 RAGForge 改成聊天产品。我们的边界是：
  • 应答能力是可选开关（KB 级 + API 级两级控制）。
  • 应答必须带 citations，无引用的回答会被拦截。
  • 应答不存对话历史（不做 ChatMemory），仅做单轮 RAG-QA。多轮交给上层 Agent。

6.2 接口

POST /api/v1/answer
{
  "kbIds": [16, 17],
  "query": "Java 工程师在广州 25-30k 的常见技术栈是？",
  "retrievalStrategy": "full",
  "answerMode": "ON",        // OFF / PREVIEW / ON
  "stream": true,
  "citationStyle": "INLINE", // INLINE 文中标号 / FOOTNOTE 结尾
  "maxTokens": 800
}

响应（SSE 流式）：
{
  "answer": "广州 25-30k Java 岗位最常见的技术栈是 [1] ...",
  "citations": [
    { "id": 1, "chunkId": 9912, "docId": 882, "title": "...", "score": 0.81,
      "spanStart": 1240, "spanEnd": 1380 }
  ],
  "retrieval": { /* 复用 SearchResponse */ },
  "tokens": { "prompt": 1820, "completion": 412 },
  "latency": { "retrieval": 380, "llm": 2100, "total": 2520 }
}

6.3 模块设计

AnswerService
  ├─ RetrievalPhase     ── 调 RetrievalService.search(...)
  ├─ PromptBuilder      ── 模板可在 KB 级配置；强制 citation 占位符
  ├─ LlmClient          ── DashScope / DeepSeek / 私有 vLLM（SPI）
  ├─ CitationLinker     ── 后处理：把 [n] 与 retrieval chunk 绑定，校验
  ├─ GuardRails         ── 答非所问 / 无引用 / PII 泄漏 拦截
  └─ AnswerAudit        ── 写 answer_logs（query / chunkIds / answer / tokens）

6.4 模型选择策略

场景模型理由
默认 PREVIEW 模式（演示）Qwen-Plus / DeepSeek-V3性价比高
正式 ON 模式（高质量）Qwen-Max / Claude Sonnet 4.6引用准确性
私有化vLLM + Qwen 2.5 14B 自托管合规客户

6.5 前端体现

  • 新增 「Answer Playground」 页：左 query + 参数；右 流式 answer + 可点击的引用块；点击引用跳转到 DocumentDetail 高亮原文。
  • DebugConsole 增加「开启应答预览」开关，复用同一 AnswerService。
验收：100 条评测 query，应答必带引用，引用准确率 ≥ 90%，"无中生有"率 < 3%。

7. 能力 4：对象存储（OSS）切换REPLACE

7.1 当前问题

  • 文件存 /data/files/ 本机磁盘 → API 实例和 Worker 实例必须共享卷 → 无法水平扩容。
  • 磁盘容量与 ECS 绑死 → 容量天花板 = 单盘上限。
  • 没有版本、没有生命周期、没有冷热分层。

7.2 抽象：ObjectStorage SPI

public interface ObjectStorage {
  StoragePutResult put(String key, InputStream in, ObjectMeta meta);
  InputStream get(String key);
  String presignedGet(String key, Duration ttl);
  String presignedPut(String key, Duration ttl, ObjectMeta meta);
  void delete(String key);
  boolean exists(String key);
}

// 实现：
// - AliyunOssStorage   (生产)
// - MinioStorage       (私有化 / 本地开发)
// - LocalDiskStorage   (兼容 V4，保留兜底)

7.3 两种上传通道（V5 关键设计）

不一刀切。保留两个入口，汇合到同一个下游：

通道 A：后端中转（默认）              通道 B：presigned 直传（大文件 / 浏览器优化）
POST /documents (multipart)         POST /uploads/presign
        │                                  │
        ├─ 鉴权 / 校验                      ├─ 鉴权 / 签发 PUT URL + uploadToken
        ├─ 流式 PUT → OSS                   │
        │                            客户端 PUT 文件 → OSS（不经后端）
        │                                  │
        │                            POST /documents/register (uploadToken + meta)
        │                                  │
        │                                  ├─ 校验 uploadToken (Redis 单次使用)
        │                                  ├─ headObject 校验 OSS 对象存在 + 大小一致
        │                                  │
        └──────────────┬───────────────────┘
                       ▼
         ┌─────────────────────────┐
         │  IngestService.register │  ← 共用层（不碰文件，纯指针操作）
         │  - 身份解析 + 去重判定    │
         │  - 新建 / SKIP / REPLACE │
         │  - afterCommit MQ.send  │
         └────────────┬────────────┘
                      ▼
                  MQ → Worker → ObjectStorage.get(bucket, key)
                                 ↑ 第一次真正读文件字节
场景推荐通道理由
浏览器小文件 (< 50MB)、JD 文本、爬虫、MCP、脚本A 后端中转一步到位、统一接口、客户端零 OSS 依赖
浏览器大文件 (≥ 50MB)、需要进度条 / 断点续传B presigned 直传不经后端、无 multipart 上限压力
内网批量灌数据（Worker / Connector）A 后端中转走业务接口审计清晰

自动路由：A 通道遇到 fileSize > 50MB 返回 413 + {"presignUrl": "/api/v1/uploads/presign"}， 前端 SDK 拦到自动切 B 路径，用户无感。

7.4 其他流程改造

流程V4V5
解析Worker 从本地读Worker 用 OSS SDK 流式读；PDF/Word 下载到 /tmp 处理后立即清理
下载后端中转后端返回 presigned GET URL，前端直连 OSS（5 min TTL）
删除rm -f硬覆盖时立刻删；或 rename 到 _orphan/ 走 OSS 生命周期 7 天清理
register 阶段完全不碰文件。无论 A/B 通道，register 拿到的都只是 OSS 提货单 (storageBucket + storageKey + md5)，纯 DB 操作 + 发 MQ。 Worker 才在消费时通过 ObjectStorage SDK 从 OSS 拉文件 —— 这是应用层无状态的关键。

7.5 安全

  • OSS bucket 设置 禁公共读；所有访问走 presigned URL。
  • presigned URL 的 TTL：上传 15 min，下载 5 min。
  • 租户隔离：bucket 内按 {tenantId}/{kbId}/{docId}/ 前缀，配合 RAM Policy 限制跨租户访问。
  • 大文件分片上传（≥ 100 MB）走 OSS MultipartUpload，前端拿到 uploadId 分片签名。

7.6 迁移路径（单写直切，不做双写灰度）

  1. V5.0：T1 完成后直接切 storage.backend = aliyun，新文件直写 OSS；老文件路径保持指向本地。
  2. V5.1（T12 收口）：跑一次性后台迁移任务，把存量文件从本地搬到 OSS（带 md5 校验 + 失败重试），迁移完成后更新 documents.storage_bucket / storage_key。
  3. V5.2：本地 /data/files 目录退役；LocalDiskStorage 仅保留为本地开发环境兜底。

架构师明确决定：不实现 DualWriteStorage / 不做读回落 / 不做灰度切换。 代价是切换日没有降级路径，但收益是少一层抽象、少一类故障模式、Codex 工期少 0.5 天。 对应风险由 T1 启动时的 OSS bucket 连通性 fail-fast 自检兜底。

收益：应用层无状态化达成 → 真正支持多实例水平扩容（这也是 tasks.md 的 🔜 项）。

9. 能力 6：身份、去重与硬覆盖增量更新NEW

9.1 为什么必须做

V4 当前的去重只看 (kb_id, content_md5)。这对爬虫场景几乎失效：

  • Boss 页面每次刷新都带"浏览量、刷新时间"等噪声 → md5 永远不同 → 永远去不掉重
  • 合同更新一个金额条款 → md5 完全变 → 无法识别"这是同一份合同的新版本"
  • 结果：KB 越爬越胖、检索召回里同质 chunk 重复，污染相关性排序
V5 核心决策：身份模型 + 硬覆盖式增量更新。不做版本号、不做软删除、不留历史， 简单可靠，对当前规模完全够用。

9.2 身份模型（三级优先级）

优先级字段典型来源稳定性
1externalIdBoss jobId / Confluence pageId / 内部工单号最强：业务主键
2sourceUrl资源 URL次强：URL 通常稳定
3contentMd5规范化字节哈希最弱：内容微变即失效

调用方在 IngestCommand.identity 里至少填一个，按非空优先级匹配。

9.3 OnConflict 三种策略

策略含义典型场景
REJECT身份冲突 → 409，调用方决定下一步前端手动上传，默认
SKIP身份冲突 + md5 一致 → 直接返回老 docId，无副作用爬虫定时全量重爬
REPLACE身份冲突 + md5 变化 → 原地硬覆盖（docId 不变）爬虫主动更新 / 替换文档按钮

9.4 数据模型变更（V19）

  ADD COLUMN source_url  VARCHAR(1024),

  WHERE external_id IS NOT NULL;

9.5 REPLACE 完整流程（docId 不变）

IngestService.register(cmd) 在事务内：

  1. 按 identity 查现有 docId（externalId → sourceUrl → md5 优先级）

  2a. 没找到 → 走"新建"路径，INSERT + MQ.send(PROCESS, newDocId)

  2b. 找到 → 比较 content_md5：
      ├─ 一致 + onConflict=SKIP → 返回 oldDocId，无副作用（爬虫省钱）
      ├─ onConflict=REJECT → 409 Conflict
      └─ onConflict=REPLACE + md5 变化 → 走"替换"路径 ↓

  3. 替换路径（事务内）：
      a) 标记 doc.parse_status = REPROCESSING
      b) DELETE FROM document_chunks WHERE document_id = oldDocId
      c) UPDATE documents SET
            storage_key  = newKey,
            content_md5  = newMd5,
            file_size    = newSize,
            filename     = newFilename,
            chunk_count  = 0,
            updated_at   = NOW(),
            parse_status = PENDING
         WHERE id = oldDocId

  4. afterCommit（事务提交后）：
      - MQ.send(PROCESS, oldDocId)
      - ES.deleteByQuery(document_id = oldDocId)
      - objectStorage.delete(bucket, oldStorageKey)   // 不留历史

9.6 Worker 视角与状态机

关键事实：Worker 完全不知道这是替换还是新建。事务已经把现场清干净 （DB chunks 删了、状态置回 PENDING、storage_key 指向新文件、ES 旧索引清了）， Worker 收到 MQ 消息只看到"一个 PENDING 的 doc 等被处理"，复用 V4 已有管道。

状态机：

  COMPLETED ──REPLACE触发──▶ PENDING ──Worker接管──▶ PROCESSING
                                                       │
                                ┌──────────────────────┼──────────────────────┐
                                ▼                                             ▼
                            COMPLETED                                       FAILED
                            (新 chunks 全部就绪)                             (errorMsg 记录)
                                                                              │
                                                                              ▼
                                                                      用户点"重新处理"
                                                                       → PENDING → ...

Worker 收到 PROCESS(docId) 后：

  1. doc = documentMapper.selectById(docId)
  2. 幂等守卫：
     ├─ doc == null            → ACK 丢弃
     ├─ status == COMPLETED    → ACK 跳过（已被另一条消息处理）
     └─ status == PROCESSING   → ACK 跳过，除非 updated_at > 5 分钟前（卡死复活）
  3. CAS 更新：status = PROCESSING（更新影响 0 行就退出）
  4. objectStorage.get(bucket, doc.storage_key)   ← 拉的是新文件
  5. Parser → Cleaner → Chunker → Embedder → Indexer
     · 所有 chunk 全部重新 embedding（不复用旧的）
     · 新 chunk_id 全部由 BIGSERIAL 重新分配
  6. UPDATE doc SET status=COMPLETED, chunk_count=N

9.7 关键约束与注意点

① 所有 chunk 必须重新 embedding

不复用任何旧 embedding。原因：

  • 内容微变即可让递归/语义分块的边界整体偏移，无法可靠对齐
  • embedding 模型可能升级，混用会有兼容性风险
  • 简单 == 可靠，硬覆盖的核心价值是"新文档完全重生"

成本估算：50 chunk 的文档 ≈ 50 次 embedding ≈ 0.001 元；爬虫每天 100 条更新 ≈ 一年 36 元。不值得为这点钱搞 diff 优化。

② 重处理期间的"窗口期"

从事务提交到 Worker 处理完之间，doc 的 chunks 是空的。搜索接口必须过滤掉非 COMPLETED 的 doc：

// RetrievalService 内统一加
queryWrapper.eq(Document::getParseStatus, "COMPLETED");

前端 DocumentDetail 显式画出 PROCESSING 状态条 + 进度提示，让用户知道"为什么搜不到"。

③ ES / OSS 删除放在 afterCommit

事务里只动 DB（chunks 删除 + documents 更新）。ES.deleteByQuery、OSS.delete 走 TransactionSynchronizationManager.afterCommit，保证 DB 是唯一真实来源：

final String oldKey = doc.getStorageKey();   // 事务开始时读，避免被 UPDATE 覆盖
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override public void afterCommit() {
            esIndexer.deleteChunksOfDoc(oldDocId);
            objectStorage.delete(bucket, oldKey);
            mqProducer.send(PROCESS, oldDocId);
        }
    });

④ 爬虫 md5 必须规范化

对 JD / 网页这类含噪声的源，不要 hash 整页 HTML，先拼接业务字段：

canonical = f"{title}|{desc}|{requirements}|{salary_min}-{salary_max}"
content_md5 = hashlib.md5(canonical.encode()).hexdigest()

否则 SKIP 永远命中不了，每次都触发 REPLACE，embedding 费用白烧。

⑤ 并发安全：同一 docId 连续两次 REPLACE

  • 第二次 REPLACE 的事务会覆盖第一次的 storage_key（取的是事务开始时刻的 oldKey 删除）
  • Worker 拿到第一条 MQ → CAS 成功 → 拉到的实际是第二次的文件（DB 已被覆盖）
  • Worker 拿到第二条 MQ → CAS 失败（status=PROCESSING）→ ACK 跳过
  • 最终结果是正确的：用第二次的内容，无任何残留

⑥ Worker 卡死的复活机制

CAS 更新加宽容窗口，避免上次卡死导致再也进不来：

UPDATE documents
SET status = 'PROCESSING', updated_at = NOW()
WHERE id = ?
  AND (status = 'PENDING'
       OR (status = 'PROCESSING' AND updated_at < NOW() - INTERVAL '5 minutes'));

⑦ 评测集和 AnswerLog 的 chunk_id 失效

硬覆盖让 chunk_id 全部重新分配。两个补丁：

  • EvaluationLab 评测集存 (document_id, expected_text_snippet) 而非 硬绑 expected_chunk_ids，运行时按文本近似匹配
  • AnswerLog 持久化引用 chunk 的文本快照到 citations_snapshot， 回看不依赖 chunks 表

9.8 Python 爬虫最终样子

def push_jd(jd):
    # 规范化 md5：只 hash 业务字段，过滤页面噪声
    canonical = f"{jd['title']}|{jd['desc']}|{jd['req']}|{jd['salary']}"
    content_md5 = hashlib.md5(canonical.encode()).hexdigest()

    files = {"file": (f"boss-{jd['job_id']}.html", jd["raw_html"], "text/html")}
    data = {"meta": json.dumps({
        "kbId": 16,
        "identity": {
            "externalId": f"boss:{jd['job_id']}",
            "sourceUrl": jd["url"],
            "contentMd5": content_md5,
        },
        "onConflict": "REPLACE",        # 变了就硬覆盖
        "ingestSource": "boss-scraper",
        "metadata": {...},
    })}
    r = requests.post(f"{RAGFORGE}/api/v1/documents",
                      files=files, data=data,
                      headers={"X-Api-Key": API_KEY})
    body = r.json()
    # status: CREATED / SKIPPED / REPLACED
    print(body["status"], body["documentId"])

9.9 三种返回状态

status含义HTTP
CREATED新建文档201
SKIPPED身份已存在且 md5 一致，未改动200
REPLACED身份已存在但 md5 变化，已原地覆盖，正在重处理200
—身份冲突 + onConflict=REJECT409
验收：boss-scraper 重爬 100 条 JD（其中 70 条内容未变、30 条薪资变了）， 系统应：70 个 SKIPPED（0 次 embedding 调用）、30 个 REPLACED（每个文档重新 embedding）、 KB 内 doc 数量不增加。
